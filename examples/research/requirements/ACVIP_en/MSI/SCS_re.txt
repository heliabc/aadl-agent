The top-level system package shall be named SCS, with explicit import dependencies on four external packages: SimpleSensor, Controller, Infrastructure, and Brake. The SCS package shall not redefine component types, bus types, or data types already defined in the imported dependent packages, and shall exclusively reference existing implementations from imported packages for all subcomponent instantiation. The SCS package shall define an abstract system type named HighLevelSCS with no externally exposed top-level ports, and a corresponding system implementation named HighLevelSCS.i. The HighLevelSCS.i implementation shall contain seven internal subcomponent instances. The first subcomponent, named sensor1, shall be a device instance bound to the SimpleSensor.i device implementation defined in the SimpleSensor package. The second subcomponent, named controller1, shall be a system instance bound to the SimpleController.i system implementation defined in the Controller package. The third subcomponent, named brake1, shall be a device instance bound to the SimpleBrake.i device implementation defined in the Brake package. The fourth subcomponent, named canBus, shall be a bus instance bound to the CanBus.i bus implementation defined in the Infrastructure package. The fifth subcomponent, named bus1553, shall be a bus instance bound to the Bus1553.i bus implementation defined in the Infrastructure package. The sixth subcomponent, named powerSource, shall be a system instance bound to the PowerSource.i system implementation defined in the Infrastructure package. The seventh subcomponent, named power, shall be a bus instance bound to the generic power bus implementation defined under the power category of the Infrastructure package. All subcomponents shall be fully contained within the HighLevelSCS.i boundary, with no direct cross-hierarchy exposure of internal interfaces outside the HighLevelSCS system boundary.

Each subcomponent shall expose interfaces with direction and type matching the definitions in its bound implementation. The sensor1 device shall expose a unidirectional outgoing data port named dataOut, a bidirectional bus access port named busOut, and a unidirectional incoming power access port named powerIn. The controller1 system shall expose a unidirectional incoming data port named dataIn, a unidirectional outgoing data port named dataOut, a bidirectional bus access port named busIn, a bidirectional bus access port named busOut, and a unidirectional incoming power access port named powerIn. The brake1 device shall expose a unidirectional incoming data port named dataIn, a bidirectional bus access port named busIn, and a unidirectional incoming power access port named powerIn. All bus instances shall support bidirectional access connections, with the power distribution bus supporting multi-drop access to deliver power to all connected powered components. Two unidirectional port connections shall be established for business data transmission. The first connection, named c1, shall link the dataOut port of sensor1 to the dataIn port of controller1. The second connection, named c2, shall link the dataOut port of controller1 to the dataIn port of brake1. Seven bidirectional bus access connections shall be established to support physical layer connectivity and power distribution. The first bus connection, named bus1, shall link the busOut port of sensor1 to the bus1553 instance. The second bus connection, named bus2, shall link the busIn port of controller1 to the bus1553 instance. The third bus connection, named bus3, shall link the busOut port of controller1 to the canBus instance. The fourth bus connection, named bus4, shall link the busIn port of brake1 to the canBus instance. The fifth bus connection, named bus5, shall link the power bus instance to the powerIn port of sensor1. The sixth bus connection, named bus6, shall link the power bus instance to the powerIn port of brake1. The seventh bus connection, named bus7, shall link the power bus instance to the powerIn port of controller1.

The system shall define one complete end-to-end data flow path named ete1. The source of this end-to-end flow shall be the internal sensorFlow flow source defined within the sensor1 device. Data from the flow source shall traverse port connection c1 to reach the controller1 system, pass through the internal controllerFlow flow path defined within controller1, then traverse port connection c2 to reach the brake1 device, and terminate at the internal brakeFlow flow sink defined within brake1, forming a complete data path from sensor perception input to brake actuation output. No cross-component business data transmission shall occur outside this defined end-to-end flow path. Port connection c1 shall exclusively carry raw perception data transmitted from the sensor to the controller, and port connection c2 shall exclusively carry actuation control commands transmitted from the controller to the brake. Bus access connections shall provide physical transmission bearer for corresponding data port connections, with all data frames on connection c1 bound for transmission over the bus1553 physical bus, and all data frames on connection c2 bound for transmission over the canBus physical bus. The power distribution bus shall not carry any business data traffic, and shall only provide continuous operating power to all connected powered components. The 1553 bus and CAN bus shall only carry business data traffic explicitly bound to them, and shall not forward unbound business data across bus domains.

Timing and latency constraints shall be enforced for all transmission paths and components. The inherent transmission latency of the canBus instance shall be constrained to the interval of 13 milliseconds to 15 milliseconds. The inherent transmission latency of the bus1553 instance shall be fixed at 7 milliseconds with zero allowable deviation. The single-segment latency for both data port connections c1 and c2 shall be uniformly constrained to the interval of 15 milliseconds to 25 milliseconds. The total end-to-end latency of flow ete1, measured from the moment data is emitted from the sensor1 flow source to the moment data is fully received and processed at the brake1 flow sink, shall be constrained to the interval of 30 milliseconds to 40 milliseconds. All latency constraints shall be mandatorily enforced in system scheduling configuration, with no scenario allowed where transmission or processing latency exceeds the defined upper bound. The defined lower latency bound shall serve as the baseline for minimum system processing and transmission overhead, and no unnecessary waiting or buffering mechanisms shall be introduced to artificially increase transmission delay beyond the lower bound requirement.

Data types for all cross-component data port transmissions shall match the port data type definitions in the corresponding imported packages. The data type output from the sensor1 dataOut port shall be fully compatible with the data type accepted by the controller1 dataIn port, and the data type output from the controller1 dataOut port shall be fully compatible with the data type accepted by the brake1 dataIn port. No port connections with mismatched data types shall be permitted. The system shall define three categories of communication buses with distinct functional roles. The first category is the MIL-STD-1553 bus, represented by the bus1553 instance, which shall carry perception data transmission from the sensor to the controller, support bidirectional bus access mechanisms, and adhere to the fixed 7 millisecond latency constraint. The second category is the CAN bus, represented by the canBus instance, which shall carry control command transmission from the controller to the brake actuator, support bidirectional bus access mechanisms, and adhere to the 13 millisecond to 15 millisecond latency interval constraint. The third category is the power distribution bus, represented by the power instance, which belongs to the generic power supply subclass, shall deliver operating power to the sensor, controller, and brake actuator, shall not carry business data traffic, and has no business data transmission latency requirement. All bus access connections shall strictly comply with the protocol requirements of the connected bus, and bus access ports on component sides shall implement the corresponding bus protocol stack logic to ensure compatibility with the connected bus instance. Bus binding rules shall be strictly enforced: connections designated for transmission over the 1553 bus shall not be routed to the CAN bus, connections designated for transmission over the CAN bus shall not be routed to the 1553 bus, and power distribution connections shall not be mixed with business data buses.
