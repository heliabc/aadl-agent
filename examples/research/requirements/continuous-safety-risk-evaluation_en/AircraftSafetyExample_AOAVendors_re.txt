The system shall define a public AADL package with the fully qualified name AircraftSafetyExample::AOAVendors to encapsulate angle-of-attack sensor vendor variant implementations and associated aircraft system configuration variants targeted for aviation safety analysis. This package shall declare a formal dependency on the public package AircraftSafetyExample::AOADiscrepancy, and shall apply a rename clause to make all public elements declared in AircraftSafetyExample::AOADiscrepancy directly accessible within the AOAVendors package scope without requiring fully qualified name references. The package shall contain two device implementation variants for the existing angle-of-attack sensor device type, and four extended system implementation variants that bind specific sensor vendor implementations to predefined aircraft safety analysis configurations. The first device implementation, identified as aoasensor.vendorA, shall represent the angle-of-attack sensor unit supplied by Vendor A. The second device implementation, identified as aoasensor.vendorB, shall represent the angle-of-attack sensor unit supplied by Vendor B. The four system implementations shall each extend a pre-existing system implementation from the imported AOADiscrepancy package: ac.OSVAPermanentDiscrepancyFail shall extend ac.OSSPermanentDiscrepancyFail, ac.OSVBPermanentDiscrepancyFail shall extend ac.OSSPermanentDiscrepancyFail, ac.OSVBNoACCKnowledge shall extend ac.OSSNoACCKnowledge, and ac.OneSensorVB shall extend ac.OneSensorSpec. Each system implementation shall refine its declared aoa1 and aoa2 angle-of-attack sensor subcomponents to bind to the specified vendor sensor implementation, with ac.OSVAPermanentDiscrepancyFail binding both sensors to aoasensor.vendorA, and ac.OSVBPermanentDiscrepancyFail, ac.OSVBNoACCKnowledge, and ac.OneSensorVB binding both sensors to aoasensor.vendorB.

All device implementations for the aoasensor type shall fully inherit every external feature, port interface, and non-error-model property association defined for the base aoasensor device type specified in the AircraftSafetyExample::AOADiscrepancy package. No additional external ports, features, or access points shall be defined for either the aoasensor.vendorA or aoasensor.vendorB implementation. Each sensor implementation shall include an embedded EMV2 error model annex to define failure characteristics for the sensor reading output, with no modifications to nominal functional interface behavior. All extended system implementations in the package shall fully inherit all external system interfaces, internal functional subcomponents, connection topology, and core behavioral logic defined in their respective parent system implementations from the AOADiscrepancy package. No additional external system interfaces, internal functional processing components, or internal connection endpoints shall be added to any extended system implementation; the only structural modification applied to each parent implementation shall be the type refinement of the aoa1 and aoa2 sensor subcomponents to the specified vendor sensor implementation.

All end-to-end data flow paths defined in the parent system implementations from the AOADiscrepancy package shall be preserved without modification across all vendor-specific system variants. Angle-of-attack measurement data generated by the instantiated vendor-specific aoasensor subcomponents shall traverse the existing internal connection paths to all designated downstream components, including the augmentation control computer, flight surface actuation components, discrepancy detection indicator, and pilot interaction interface, as specified in the base system configurations. No new data flow paths shall be introduced, and no existing data flow paths shall be removed, rerouted, or re-prioritized in any of the vendor-specific system implementations. Error propagation paths associated with sensor reading failures shall follow the same connection topology as nominal measurement data to support consistent safety analysis across vendor variants.

All nominal timing, scheduling partition assignments, execution time budgets, period constraints, and end-to-end latency requirements defined for the base aoasensor device type and parent system implementations in the AOADiscrepancy package shall apply without modification to both vendor A and vendor B sensor implementations, as well as to all extended vendor-specific system configurations. No additional scheduling rules, dispatch protocols, execution time allocations, or latency bounds shall be introduced for the vendor-specific variants, as the variants differ only in probabilistic sensor failure characteristics rather than nominal operational timing behavior. Error event occurrence timing for sensor reading failures shall follow the probabilistic distribution defined in the EMV2 annex for each sensor implementation, with no fixed temporal trigger for failure events specified for nominal operation.

All data type definitions for angle-of-attack sensor readings, augmentation control computer commands, flight surface control signals, discrepancy indicator status values, and pilot input/output signals used across the vendor-specific implementations shall be inherited directly from the AircraftSafetyExample::AOADiscrepancy package. No new data type definitions shall be declared within the AOAVendors package. All communication bus definitions, protocol specifications, bus access bindings, and data transfer property associations defined for the base system configurations shall remain in full effect for all vendor-specific system variants. No new bus types, bus instances, or bus access connections shall be defined or added within the AOAVendors package. The only unique property assignments specified within the package shall be the EMV2 occurrence distribution properties for the sensor reading failure event: aoasensor.vendorA shall assign a probability value of 1.5E-5 to the reading failure occurrence, and aoasensor.vendorB shall assign a probability value of 2.5E-4 to the reading failure occurrence. These properties shall be used exclusively for safety and reliability analysis, and shall not alter nominal data encoding, bus transfer behavior, or data validity rules for operational system execution.
