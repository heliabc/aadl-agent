A public AADL package named PhysicalParts shall be defined as the top-level naming container for all modeling elements associated with embedded hardware physical components. All elements contained within this package shall fall within the physical parts modeling domain, and no dependencies on elements imported from external packages shall be introduced, with all type references resolved to locally defined entries within the package. The package shall contain five categories of top-level type definitions, covering a processor type, a communication bus type, a memory type, a system type, and an abstract type. The system type named main_board shall include one implementation variant identified as single, and this implementation shall exclusively rely on the locally defined powerpc processor type, main_memory memory type, and CANbus bus type to construct its internal subcomponent structure, with no additional external component or type dependencies.

All top-level component types defined within the package, including the powerpc processor, CANbus bus, main_memory memory, main_board system, and Power abstract type, shall be constructed as base type placeholders with no externally exposed ports, functional access points, or data interaction interfaces; no input ports, output ports, provided service points, required service points, or parameter interfaces shall be declared for these top-level types. The main_board.single system implementation shall declare three internal subcomponent instances: a processor instance named cpu typed as powerpc, a memory instance named ram typed as main_memory, and a bus instance named canbus typed as CANbus. No explicit interface connections between internal subcomponents shall be defined in this implementation, no internal ports or access points shall be declared for the implementation’s external boundary, and all contained subcomponents shall carry no dedicated interaction interfaces to support cross-component communication.

No explicit data interaction ports, connection paths, or data access links shall be defined across all component types and the system implementation within the package. No fixed end-to-end data transmission path across components shall be specified within the current modeling scope, and no preconfigured data interaction channel shall exist between internal subcomponents, or between the main_board system and its external operating environment.

No scheduling attributes, periodic execution attributes, execution time attributes, or latency constraint attributes shall be configured for any component defined within the package. The powerpc processor shall not be bound to a specific scheduling policy, the main_memory memory shall not define mandatory memory access latency parameters, and the CANbus bus shall not define transmission latency or bus arbitration timing rules. The main_board system and its single implementation shall not declare timing-related constraints including end-to-end latency, scheduling period, or execution deadline, with all timing-related properties reserved for subsequent model extension and refinement.

A single abstract base type named Power shall be defined within the package; this type shall serve as a base placeholder with no internal fields, value constraints, or structural definitions, to support subsequent extension of power-related attributes without defining concrete data structures, value ranges, or encoding rules at the current modeling stage. A single communication bus type named CANbus shall be defined within the package as a base bus type placeholder, with no configured transmission protocol parameters, baud rate, frame format, or bus arbitration rules, to support subsequent bus attribute refinement and connection binding for CAN-class physical communication links. The powerpc processor type shall be defined as a base placeholder for general PowerPC architecture processors, with no specified instruction set, core frequency, core count, or other granular hardware parameters. The main_memory memory type shall be defined as a base placeholder for on-board main memory hardware, with no specified storage capacity, access bit width, read/write rate, or other memory-specific parameters. All type definitions within the package shall follow a minimal placeholder rule that only clarifies the AADL category of each element without attaching granular hardware attributes, to support incremental refinement of hardware details in follow-up modeling activities.
