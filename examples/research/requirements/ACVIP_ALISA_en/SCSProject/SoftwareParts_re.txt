The system shall be contained within a top-level AADL package named SoftwareParts, which shall declare a formal import dependency on the external DataModel package to access pre-defined shared data type definitions, with no other external package dependencies. The SoftwareParts package shall define a top-level system type named DigitalControl, with one concrete system implementation identified as DigitalControl.tier1. The DigitalControl.tier1 implementation shall decompose into two generic process subcomponents with no specified concrete process type: a process subcomponent named IO_Process, and a process subcomponent named Command_Process, with no additional subcomponents specified at the top system tier. Two concrete process types shall be defined within the package to support eventual binding to these generic process subcomponents: IO_Process and Command_Process, each with one concrete implementation. The IO_Process.impl process implementation shall contain three thread subcomponents: an instance of the sensor_sense_thread type named sense, a generic thread subcomponent with no specified concrete thread type named mode_change, and an instance of the actuator_output_thread type named actuate. The Command_Process.impl process implementation shall contain three thread subcomponents: an instance of the filterApp thread type named filter, a generic thread subcomponent with no specified concrete thread type named pilot, and an instance of the controlApp thread type named control.

The DigitalControl system type, IO_Process process type, and Command_Process process type shall not define any externally facing port features, as no interface declarations are associated with these component type definitions. The sensor_sense_thread type shall expose two unidirectional data port interfaces: an incoming data port named signalin for reception of raw sensor input, and an outgoing data port named signalout for transmission of acquired sensor data to downstream processing logic. The actuator_output_thread type shall expose two unidirectional data port interfaces: an incoming data port named controlin for reception of computed actuation commands from upstream control logic, and an outgoing data port named actuate for transmission of final actuation signals to external actuator hardware. The filterApp thread type shall expose two unidirectional data port interfaces: an incoming data port named sensorraw for reception of raw sensor data from upstream sensing logic, and an outgoing data port named sensorfiltered for transmission of processed, filtered sensor data to downstream control logic. The controlApp thread type shall expose two unidirectional data port interfaces: an incoming data port named sensorfiltered for reception of filtered sensor data from upstream filtering logic, and an outgoing data port named actuatesensor for transmission of newly calculated actuation commands to downstream output logic. The generic mode_change thread within IO_Process and the generic pilot thread within Command_Process shall not define any explicit port features, as no specialized type or interface declarations are associated with these base thread instances.

The port definitions on the specialized thread types establish type-compatible endpoint pairs that define the intended logical closed-loop control data path, though explicit port connections and required cross-hierarchy port delegations are not specified in the current component structure, as no port features are declared on process or system component types and no connection declarations exist at any hierarchical level. The type-aligned logical path originates at the signalin input port of sensor_sense_thread, which is intended to receive raw sensor data from external sensing sources. The signalout output port of sensor_sense_thread, which carries SensorData type values, is type-compatible with the sensorraw input port of filterApp, which also carries SensorData type values, forming a logical sensing to filtering link. The sensorfiltered output port of filterApp, which carries SensorData type values, is type-compatible with the sensorfiltered input port of controlApp, which also carries SensorData type values, forming a logical filtering to control calculation link. The actuatesensor output port of controlApp, which carries actuatecmd type values, is type-compatible with the controlin input port of actuator_output_thread, which also carries actuatecmd type values, forming a logical control calculation to output link. The actuate output port of actuator_output_thread, which carries actuatecmd type values, is intended to transmit final actuation signals to external actuator hardware. No logical data flow paths are defined for the generic mode_change and pilot thread instances, as these components lack declared port features to support connection to other system elements.

All specialized thread types with defined properties shall support periodic dispatch with a common 20 ms period. The sensor_sense_thread shall be allocated a 10 Kbyte worst-case stack size, with per-dispatch compute execution time bounded between a minimum of 10 ms and a maximum of 12 ms. The actuator_output_thread shall be allocated a 10 Kbyte worst-case stack size, with per-dispatch compute execution time bounded between a minimum of 8 ms and a maximum of 10 ms. The filterApp thread shall be allocated a 25 Kbyte worst-case stack size, plus a 250 Kbyte private data memory region reserved for logging operations, with per-dispatch compute execution time bounded between a minimum of 5 ms and a maximum of 7 ms. The controlApp thread shall be allocated a 25 Kbyte worst-case stack size, plus a 50 Kbyte private data memory region reserved for persistent control state storage, with per-dispatch compute execution time bounded between a minimum of 2 ms and a maximum of 6 ms. No scheduling period, execution time bound, stack size, or private memory allocation properties are specified for the generic mode_change and pilot thread instances, nor for the generic IO_Process and Command_Process process subcomponents at the system tier. No explicit end-to-end latency bounds are defined for any data path in the current specification.

All data exchanged via thread data ports shall use typed data definitions imported from the external DataModel package. The SensorData data type from the DataModel package shall be used for all sensor measurement transfers, including raw sensor data carried on the signalin and signalout ports of sensor_sense_thread, the sensorraw input port of filterApp, and the paired sensorfiltered ports of filterApp and controlApp. The actuatecmd data type from the DataModel package shall be used for all actuation command transfers, including the actuatesensor output port of controlApp, the controlin input port of actuator_output_thread, and the actuate output port of actuator_output_thread. No custom data type definitions shall be declared within the SoftwareParts package. No dedicated communication bus components, bus access interfaces, or bus-associated communication properties shall be defined within the SoftwareParts package, meaning inter-thread and inter-process data transfer mechanisms are not constrained to a specific physical or logical bus implementation at this specification level.
