The system shall define a top-level AADL package named wheel with a public scope enclosing all contained model elements. The wheel package shall declare an explicit dependency on the common package to access pre-defined shared model elements hosted in the common namespace. The wheel package shall define an abstract root system type named wheel that acts as the common base for all wheel component variants, with no concrete features or implementation defined for this root type. The package shall include two concrete wheel system type variants, the first named wheel_one_input which extends the base wheel type to represent a single-input wheel implementation that abstracts dual physical supply channels from two pump sources into a single logical interface, and the second named wheel_two_inputs which extends the wheel_one_input type directly to represent a dual-input wheel implementation that explicitly models independent supply channels connected to separate pump units. Each concrete wheel system type shall be paired with a corresponding system implementation artifact, identified as wheel_one_input.i for the single-input variant and wheel_two_inputs.i for the dual-input variant, with no internal subcomponents declared in either implementation at the current abstraction level.

The abstract base wheel system type shall expose no external interface features. The wheel_one_input system type shall define a single required bus access feature named input, which forms the external connection point for pressure signaling to the single-input wheel variant. As an abstracted model, the wheel_one_input variant shall not expose separate interfaces for redundant physical supply channels, instead collapsing dual channel connectivity into the single input interface. The wheel_two_inputs system type shall inherit the input required bus access feature from its parent type wheel_one_input, and shall define two additional required bus access features named green_input and blue_input respectively to represent explicit independent supply channels from separate pump units, aligning with the explicit dual-channel modeling approach for this variant. Neither wheel system implementation shall define internal subcomponents, private connection points, or internal interface endpoints, as both implementations are modeled as black-box elements at the current level of abstraction. For the wheel_one_input variant, the input required bus access interface shall support inbound error propagation for the NoService error condition, as specified in the component's error model annex. For the wheel_two_inputs variant, the green_input and blue_input required bus access interfaces shall each support inbound error propagation for the NoService error condition, as specified in the component's own error model annex which fully replaces the inherited error model specification from the parent type; no error propagation behavior is defined for the inherited input interface in the dual-input wheel variant.

At the current abstraction level, no internal data processing paths, data transformation logic, or internal component-to-component data flows shall be defined within either wheel implementation, as no internal subcomponents are present to route or process data. All pressure-related signaling delivered to wheel components shall traverse the connected required bus access interfaces from external source elements. For the wheel_one_input variant, all incoming pressure signaling shall be delivered via the single input bus interface, with dual redundant channel aggregation from two pump sources handled outside the scope of the wheel component model, consistent with the abstracted single-channel representation. For the wheel_two_inputs variant, pressure signaling may be delivered via the inherited input interface as well as the two explicit channel interfaces green_input and blue_input; the green_input and blue_input interfaces are intended to carry pressure signaling directly from independent pump sources without pre-aggregation at the wheel interface boundary, aligning with the explicit dual-channel modeling intent for this variant. No outbound data flows from wheel components to external connected elements are defined in the current model scope.

No thread or process subcomponents are defined within the wheel system implementations, so no periodic or aperiodic task scheduling rules, thread execution time budgets, processor allocation constraints, or end-to-end data path latency limits shall be specified for wheel components at the current abstraction level. All wheel components with defined error behavior shall implement state transition logic aligned with the referenced simple error behavior specification from the common error library. The wheel_one_input component shall initialize in the Operational state upon system start, and shall transition immediately to the Failed state upon detection of a NoService error event propagated inward through the input bus interface. The wheel_two_inputs component shall initialize in the Operational state upon system start, and shall transition immediately to the Failed state upon detection of a NoService error event propagated inward through either the green_input bus interface or the blue_input bus interface; no state transitions triggered by error events on the inherited input interface are defined for the dual-input wheel variant. No intermediate degraded operational states, error recovery transitions, or outbound error propagation from wheel components to external connected elements shall be defined in the current model scope.

All communication between wheel components and external connected elements shall use the pressure.i bus implementation defined in the common package, accessed via the required bus access features declared on each wheel component. No custom data type definitions shall be declared within the wheel package itself; all data type specifications used for pressure communication shall be sourced from the dependent common package. Error modeling logic for all wheel components shall reference type definitions from the error_library namespace, and shall utilize the simple error behavior definition from that library to specify component state transitions. The NoService error type used for inbound interface error propagations shall be sourced from the referenced error_library type collection. For the wheel_one_input variant, the single connected pressure.i bus instance accessed via the input interface shall carry aggregated signaling from two physical pump supply channels, with redundancy management for the dual channels implemented at a layer external to the wheel component model. For the wheel_two_inputs variant, the green_input and blue_input interfaces shall each connect to a separate instance of the common::pressure.i bus, corresponding to independent supply channels linked to separate pump units to support explicit dual-channel representation, with no logical channel aggregation performed at the wheel component interface for these two connections.
