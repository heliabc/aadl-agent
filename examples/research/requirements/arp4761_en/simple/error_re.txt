A public AADL package named error_library shall be constructed as an independent reusable error modeling repository. The package shall have no external dependencies on other AADL packages, and shall embed an EMV2 annex to host standardized error modeling artifacts. All elements defined within the package shall be publicly accessible to all external AADL models that import the library via with statements. The package shall not contain instantiable runtime components such as hardware, software, or concrete system implementation units, and shall only provide reusable error type definitions and error behavior state machine templates to support consistent error modeling for upper-level system components.

As a static modeling definition repository, the error_library package shall not define instantiable runtime components including processes, threads, devices, processors, or bus components. No runtime functional interaction ports, internal component connection interfaces, or feature access points shall be specified within the package. All artifacts contained in the package shall serve as type-level modeling templates, and shall not define runtime instance-level interaction interfaces or contract specifications.

The error_library package shall not define runtime functional components or end-to-end data interaction links, so no runtime service data flow transmission paths shall be specified within the library. Error propagation logic implied by the library’s state machine templates shall only act as a reference for upper-level component instances when configuring their proprietary error behavior, and no concrete cross-component error propagation paths or fault propagation routes shall be defined in the library.

The error_library package shall not contain schedulable runtime entities such as threads, thread groups, or processes, so no runtime scheduling rules, execution periods, latency limits, deadline constraints, dispatch protocols, or time-related execution attributes shall be specified within the library. Error events and recovery events defined in the library’s error behavior templates shall only act as type identifiers for state machine transition triggers, and shall not be bound to specific time trigger thresholds, timeout values, or occurrence probability parameters.

All error type definitions within the EMV2 annex of the package shall follow a hierarchical inheritance structure. A top-level error type NoPower shall be defined to represent power supply loss faults. A top-level error type NoService shall be defined to represent service unavailability faults. A top-level error type ValueError shall be defined to represent abnormal data value faults, and a second-level error type NoValue shall be derived from ValueError to represent complete value missing faults, with full inheritance of all attributes and propagation rules associated with the ValueError type. A top-level error type PlatformFailure shall be defined to represent generic platform-level faults, and two second-level error types shall be derived from PlatformFailure: HardwareFailure to represent physical hardware faults with full inheritance of PlatformFailure attributes, and SoftwareFailure to represent executable software faults with full inheritance of PlatformFailure attributes.

Six reusable error behavior state machine templates shall be defined within the EMV2 annex for reference by upper-level components during error model configuration. The first state machine, identified as ThreeState, shall include three mutually exclusive states: Operational as the initial state representing normal component operation, NonCriticalModeFailure representing faults that do not impact critical functional modes, and CriticalModeFailure representing faults that disrupt critical functional modes; no trigger events or state transition logic shall be defined for this state machine template. The second state machine, identified as ThreeErrorStates, shall define three error trigger events typed as error events: BadValueEvent for invalid or out-of-range value occurrences, NoValueEvent for complete missing value occurrences, and LateValueEvent for value delivery beyond allowed time windows; this state machine shall include four mutually exclusive states, with Operational as the initial normal operation state, and three dedicated fault states including BadValueState, NoValueState, and LateValueState corresponding to the three defined error events respectively; transition logic for this state machine shall specify that a component in the Operational state shall transition to BadValueState upon activation of BadValueEvent, transition to NoValueState upon activation of NoValueEvent, and transition to LateValueState upon activation of LateValueEvent; no recovery transitions or transitions between fault states shall be defined for this state machine template. The third state machine, identified as Simple, shall include two mutually exclusive states: Operational as the initial normal operation state, and Failed representing permanent, unrecovered fault conditions; no trigger events or state transition logic shall be defined for this state machine template. The fourth state machine, identified as bscu, shall include three mutually exclusive states: Operational as the initial normal operation state, Alternate representing degraded operation in backup functional mode, and Failed representing permanent fault conditions that halt all function provision; no trigger events or state transition logic shall be defined for this state machine template. The fifth state machine, identified as WBS, shall include six mutually exclusive states: Operational as the initial normal operation state, and five fault states including AnnunciatedBrakingLoss representing braking function loss with active crew alert, UnannunciatedBrakingLoss representing braking function loss without active crew alert, PartialBrakingLoss representing partial loss of braking capability, AsymmetricLoss representing unequal braking force across symmetric wheel sets, and InadvertentBrake representing uncommanded brake activation during non-braking operational phases; no trigger events or state transition logic shall be defined for this state machine template. The sixth state machine, identified as SimpleAndTransient, shall define three trigger events: Failure typed as an error event for permanent, non-recoverable fault occurrences, FailureTransient typed as an error event for temporary, recoverable fault occurrences, and ResetEvent typed as a recovery event for intentional component reset actions; this state machine shall include three mutually exclusive states, with Operational as the initial normal operation state, Failed representing permanent fault conditions, and TransientFailure representing temporary fault conditions; transition logic for this state machine shall specify that a component in the Operational state shall transition to the Failed state upon activation of the Failure event, transition to the TransientFailure state upon activation of the FailureTransient event, and a component in the TransientFailure state shall transition back to the Operational state upon activation of the ResetEvent; no recovery transition logic shall be defined for components entering the Failed state.

No communication bus types, bus implementations, bus instances, bus access interfaces, or bus-associated attributes including communication protocol specifications, bandwidth limits, transmission latency values, or fault containment rules for buses shall be defined within the error_library package. All bus-related definitions shall be supplemented by upper-level system models that import the error library, aligned with specific application scenario and architecture requirements.
