The root modeling module is a public AADL package named platform, which declares mandatory dependencies on the EMV2 error modeling annex property set and the ARP4761 aviation safety assessment property set to support error behavior specification and safety property annotation. No additional external package dependencies are permitted for this package. All component type and implementation definitions within the package are exposed as public elements, with no private component definitions included. The package defines three core component types: a virtual processor type named partition that models partition runtime management functionality for integrated modular avionics configurations, a processor type named cpu that models generic physical central processing unit hardware, and a system type named platform that acts as the top-level container for complete computing platform assemblies. Four component implementations are defined to support two distinct platform architectures: a generic virtual processor implementation named partition.generic for the partition type, which provides base partition runtime functionality without specialized configuration; two processor implementations for the cpu type, named cpu.ima for integrated modular avionics processing hardware and cpu.single for standalone federated architecture processing hardware; and two system implementations for the platform type, named platform.ima for the fully integrated modular avionics platform configuration and platform.federated for the distributed federated platform configuration. Strict dependency hierarchy is enforced across implementations: the cpu.ima processor implementation depends exclusively on the partition.generic virtual processor implementation for its internal subcomponents, the platform.ima system implementation depends exclusively on the cpu.ima processor implementation for its internal subcomponent, the platform.federated system implementation depends exclusively on the cpu.single processor implementation for its internal subcomponents, and no cross-dependencies are permitted between the integrated modular avionics and federated architecture implementation branches.

All components in the package define no functional data, event, or event data ports, with all interaction points limited to EMV2 error propagation interfaces aligned with safety modeling requirements. The partition virtual processor type defines two external error propagation interfaces: an outgoing propagation point named bindings that transmits both SoftwareFailure and HardwareFailure error types to software components bound to the partition, and an incoming propagation point named processor that receives HardwareFailure error types from the underlying physical processor hosting the partition. The partition.generic virtual processor implementation inherits all interface definitions from the partition type, defines no internal subcomponents, and adds no additional external or internal interfaces. The base cpu processor type defines a single external outgoing error propagation interface named bindings that transmits HardwareFailure error types to all hosted partition and software components. The cpu.ima processor implementation inherits the external bindings error propagation interface from the base cpu type, and defines four identical internal subcomponents instantiated from the partition.generic virtual processor, named partition1, partition2, partition3, and partition4 respectively; no additional external interfaces are added in this implementation, and each internal partition subcomponent is logically bound to the host cpu hardware to receive hardware failure propagations from the processor. The cpu.single processor implementation inherits the external bindings error propagation interface from the base cpu type, adds one additional external outgoing error propagation interface named processor that transmits SoftwareFailure error types to hosted application components, and defines no internal subcomponents to reflect the lack of separate partition runtime layers in federated standalone processors. The top-level platform system type defines no external interfaces of any kind, as it functions as a closed assembly of internal platform computing resources. The platform.ima system implementation inherits the empty external interface set from the platform type, and defines a single internal subcomponent instantiated from the cpu.ima processor, named cpu. The platform.federated system implementation inherits the empty external interface set from the platform type, and defines two identical internal subcomponents instantiated from the cpu.single processor, named cpu1 and cpu2 respectively, with no logical connection between the two processor instances to maintain fault isolation between federated resources. Each component type and implementation defines internal error events per its error behavior specification: the partition type defines an internal SoftwareFailure error event, the base cpu type defines an internal InternalFailure error event, and the cpu.single implementation defines an additional internal SoftwareFailure error event separate from the inherited hardware InternalFailure event. All components use the two-state simple error behavior model, with an initial Operational state and a terminal Failed state, where internal error events trigger a one-way transition from Operational to Failed with no recovery transitions defined.

All flows within the platform package are EMV2 error propagation flows, as no functional application data paths are defined at the platform abstraction layer. The partition virtual processor defines two formal error flows: an error source flow named fsoft that originates from the internal SoftwareFailure event and propagates out of the component via the bindings outgoing point as a SoftwareFailure error, and an error path flow named fhard that receives incoming HardwareFailure errors from the processor incoming point and passes these errors unmodified out through the bindings outgoing point. When a partition component is in the Operational state, all propagations via the bindings point carry a NoError value to indicate normal runtime operation; when a partition transitions to the Failed state due to an internal SoftwareFailure event, all propagations via the bindings point carry a SoftwareFailure value. The base cpu processor type defines a single error source flow named f1 that originates from the internal InternalFailure event and propagates out of the component via the bindings outgoing point as a HardwareFailure error. When a cpu component is in the Operational state, all propagations via the bindings point carry a NoError value; when a cpu transitions to the Failed state due to an internal InternalFailure event, all propagations via the bindings point carry a HardwareFailure value. For the cpu.ima implementation, HardwareFailure errors exiting the cpu via the bindings point are implicitly routed to the incoming processor error point of each of the four internal partition subcomponents via the standard virtual processor to physical processor binding mechanism defined in EMV2, triggering the fhard error path in each partition to pass hardware failure errors out through each partition's bindings point to hosted application software. No additional software failure flows are defined at the cpu.ima level, as all software runtime failures for integrated modular avionics configurations are contained within individual partition subcomponents rather than originating at the processor hardware layer. For the cpu.single implementation, an additional error source flow named fsoft is defined that originates from the implementation's internal SoftwareFailure event and propagates out of the component via the processor outgoing point as a SoftwareFailure error. When a cpu.single component is in the Operational state, all propagations via the processor point carry a NoError value; when a cpu.single transitions to the Failed state due to an internal SoftwareFailure event, all propagations via the processor point carry a SoftwareFailure value. The inherited hardware failure flow f1 from the base cpu type remains fully active in the cpu.single implementation, propagating hardware failures out through the original bindings point. For the platform.ima system implementation, all error flows are fully contained within the single internal cpu.ima subcomponent, with no error propagation across the platform system boundary consistent with the lack of external interfaces. For the platform.federated system implementation, all error flows are fully contained within the two isolated internal cpu.single subcomponents, with no error propagation across the platform system boundary and no error propagation connections between the two separate cpu instances to preserve federated fault isolation.

No functional task scheduling parameters, execution time budgets, partition scheduling window definitions, core allocation rules, or end-to-end functional latency constraints are specified within this platform package, as the model scope is limited to static platform structure and error propagation behavior, with those runtime configuration properties deferred to later application integration stages. No shared resource access latency or communication latency constraints are defined, as no communication resources or shared resource access protocols are modeled in this package. Temporal properties are defined exclusively for error event and error flow occurrence rates, aligned with ARP4761 safety assessment requirements. The SoftwareFailure error event on the partition virtual processor is assigned a Major failure severity classification per ARP4761, with a Probable qualitative likelihood objective; this failure applies across all operational phases, describes platform software failures such as operating system exceptions that impact all software components bound to the affected partition, and follows a Poisson occurrence distribution with a probability value of 1.35e-5 per operational exposure period, with an associated hazard entry marked with a TBD cross-reference, empty formal failure identifier, and note describing the full impact scope of the failure. The InternalFailure error event on the base cpu processor type is assigned a Major failure severity classification per ARP4761, with a Probable qualitative likelihood objective; this failure applies across all operational phases, describes hardware failures of processing components or attached devices that impact all software hosted on the affected hardware, and follows a Poisson occurrence distribution with a probability value of 1.35e-5 per operational exposure period, with an associated hazard entry marked with a TBD cross-reference, empty formal failure identifier, and note describing the full impact scope of the failure. The hardware failure error flow f1 on the base cpu type is assigned a Fixed occurrence distribution with a probability value of 6.75e-5 per operational exposure period. The SoftwareFailure error event on the cpu.single processor implementation is assigned a Major failure severity classification per ARP4761, with a Probable qualitative likelihood objective; this failure applies across all operational phases, describes platform software failures such as operating system exceptions that impact all software components hosted on the affected federated processor, and follows a Poisson occurrence distribution with a probability value of 1.35e-5 per operational exposure period, with an associated hazard entry marked with a TBD cross-reference, empty formal failure identifier, and note describing the full impact scope of the failure. No redundant error detection, fault recovery, or reconfiguration timing constraints are defined for any component, as no recovery state transitions are included in the error behavior models.

No custom application data types, error types, or data implementations are defined within the platform package. All error types used in propagation interfaces, error flows, and error behavior definitions, including NoError, SoftwareFailure, and HardwareFailure, are imported from the external public error_library package, and all error behavior logic conforms to the simple two-state error behavior state machine defined in that library. No local modification, extension, or redefinition of imported error types or behavior models is permitted within the platform package to ensure consistency across dependent system models. No physical bus components, virtual bus components, bus access interfaces, or bus-related property definitions are included in the platform package, as the current model scope is limited to computing hardware and partition runtime components without modeling inter-component communication infrastructure.
