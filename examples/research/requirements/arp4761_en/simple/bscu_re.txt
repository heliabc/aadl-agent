The top-level model module is defined as a public AADL package named bscu, which shall declare explicit import dependencies on six external packages to access shared model elements: the common package for shared command data types and power bus definitions, the platform package for federated and integrated modular avionics platform component models, the Base_Types package for primitive data type definitions, the error_library package for reusable error type and error behavior definitions, the EMV2 package for error modeling annex constructs and properties, and the ARP4761 package for safety assessment property sets aligned with aerospace safety standard requirements. No circular dependencies shall be permitted between components contained within the bscu package, and all cross-package element references shall resolve exclusively to elements declared in the explicitly imported external packages. The bscu package shall contain five core component type definitions: a command process component, a monitor process component, a bscu_subsystem system component, a select_alternate system component, and a top-level bscu system component. Each component type shall be paired with dedicated implementation definitions as required to support functional behavior and multiple deployment configurations. The top-level bscu system shall support three implementation variants: a minimal basic implementation without redundant subcomponents, a core generic implementation containing full redundant channel logic, a federated deployment implementation that extends the generic implementation for federated avionics architectures, and an integrated modular avionics (IMA) deployment implementation that extends the generic implementation for partitioned IMA architectures. The federated and IMA implementations shall inherit all features, subcomponents, connections, and error behavior from the generic bscu implementation, adding only platform-specific subcomponents and deployment binding properties.

All component interfaces shall be explicitly declared at the component type level, with no hidden external interfaces added at the implementation level. The command process component type shall expose three unidirectional data port interfaces: an output data port for generated brake command values, an output data port for generated skid command values, and an input data port for received pedal position values. The command.i implementation of the command process shall define an implicit processor error input point to receive software and hardware failure signals from the bound execution platform, with no additional external functional ports. The monitor process component type shall expose three unidirectional data port interfaces: an input data port for received brake command values, an input data port for received skid command values, and an output data port for generated channel validity status. The monitor.i implementation of the monitor process shall define an implicit processor error input point to receive software and hardware failure signals from the bound execution platform, plus an internal error event to capture spurious invalid status outputs generated without corresponding input or platform faults. The bscu_subsystem system component type shall expose five external interfaces: a required bus access interface to connect to a generic power supply, an input data port for received pedal position values, an output data port for generated brake command values, an output data port for generated skid command values, and an output data port for generated channel validity status. The bscu_subsystem.generic implementation of the bscu_subsystem shall contain two internal process subcomponents: one instance of the monitor.i process named mon, and one instance of the command.i process named cmd, with no additional external interfaces beyond those declared on the parent component type. The select_alternate system component type shall expose three unidirectional data port interfaces: two input data ports to receive validity status values from the primary and alternate BSCU channels respectively, and one output data port for the generated channel selection result. The select_alternate component shall define an internal error event to capture erroneous channel selection outputs generated without corresponding input validity faults. The top-level bscu system component type shall expose seven external interfaces: two required bus access interfaces to connect to independent generic power supplies for the primary and alternate channels, two input data ports to receive pedal position values for the primary and alternate channels respectively, an output data port for the generated alternate channel selection flag, an output data port for skid command values from the normal (primary) channel, and an output data port for skid command values from the alternate channel. The bscu.basic implementation of the top-level bscu shall contain no internal subcomponents, implementing only core error response behavior for power supply faults. The bscu.generic implementation of the top-level bscu shall contain three internal system subcomponents: two instances of the bscu_subsystem.generic component representing the primary and alternate BSCU channels, and one instance of the select_alternate component to implement channel selection logic. The bscu.federated implementation shall inherit all subcomponents and interfaces from bscu.generic, adding one internal subcomponent representing a federated avionics platform. The bscu.ima implementation shall inherit all subcomponents and interfaces from bscu.generic, adding one internal subcomponent representing a partitioned IMA platform.

All functional and error data flows between components shall be explicitly defined via port and bus access connections, with no implicit data routing permitted. All component error behavior shall reuse predefined error behavior state machines from the error_library package: the command, monitor, bscu_subsystem, and select_alternate components shall use the generic simple error behavior set, while the top-level bscu implementations shall use the dedicated bscu error behavior set from the error library to define standard operational and failed state transitions. Within each bscu_subsystem.generic instance, incoming pedal position data from the external pedal input port shall be routed directly to the pedal value input port of the internal command process subcomponent. The command process shall process received pedal position values to compute corresponding brake command and skid command output values. Generated brake command values from the command process shall be routed along two parallel paths: one path to the brake command input port of the internal monitor process subcomponent for validity checking, and a second path directly to the external brake command output port of the bscu_subsystem for delivery to downstream braking components. Generated skid command values from the command process shall be routed along two parallel paths: one path to the skid command input port of the internal monitor process subcomponent for validity checking, and a second path directly to the external skid command output port of the bscu_subsystem for delivery to downstream braking components. The monitor process shall perform validity assessments on received brake and skid command values, generating a boolean validity status that is routed directly to the external validity output port of the bscu_subsystem. At the top-level bscu.generic, bscu.federated, and bscu.ima implementations, power supplied via the first external power bus access port shall be routed exclusively to the power input of the primary bscu_subsystem instance, and power supplied via the second external power bus access port shall be routed exclusively to the power input of the alternate bscu_subsystem instance. Incoming pedal position data from the first external pedal input port shall be routed exclusively to the pedal input of the primary bscu_subsystem instance, and incoming pedal position data from the second external pedal input port shall be routed exclusively to the pedal input of the alternate bscu_subsystem instance. Validity status output from the primary bscu_subsystem instance shall be routed to the first input port of the select_alternate subcomponent, and validity status output from the alternate bscu_subsystem instance shall be routed to the second input port of the select_alternate subcomponent. The select_alternate component shall implement fixed selection logic that outputs a false value when the primary channel validity input indicates a valid primary channel, signaling use of the primary channel, and outputs a true value when the primary channel validity input indicates a primary channel fault, signaling switchover to the alternate channel. The generated selection result from the select_alternate component shall be routed directly to the external alternate selection output port of the top-level bscu. Skid command output from the primary bscu_subsystem instance shall be routed directly to the external normal channel skid command output port of the top-level bscu, and skid command output from the alternate bscu_subsystem instance shall be routed directly to the external alternate channel skid command output port of the top-level bscu. Error propagation paths shall be defined per EMV2 rules to model fault transmission across the system, supporting end-to-end fault tracing for FMEA and fault impact analysis. For the command process, a no-service error received on the pedal value input port, or software or hardware failure errors received from the bound execution platform, shall trigger a transition to a failed state, which propagates no-value errors out of both the brake and skid command output ports. For the monitor process, a no-value error received on either the brake or skid command input ports, software or hardware failure errors received from the bound execution platform, or an internal invalid report error event, shall trigger a transition to a failed state, which propagates a no-value error out of the validity status output port. For each bscu_subsystem instance, a no-power error received on the power bus access interface shall trigger a transition to a failed state, which propagates a no-value error out of the validity status output port, forming a continuous error path from power supply loss to invalid validity status output. The composite error state of each bscu_subsystem shall be marked as failed if either the internal command or monitor process is in a failed state, and shall be marked as operational only if both internal processes are in an operational state. For the select_alternate component, concurrent no-value errors received on both channel validity input ports, or an internal selection error event, shall trigger a transition to a failed state, which propagates a no-value error out of the selection result output port. For the minimal bscu.basic implementation, a no-power error received on either external power input shall trigger a transition to a failed state, with error sinks defined to capture power loss faults on both power interfaces. For the bscu.generic, federated, and ima implementations, the composite system error state shall be marked as failed only if both primary and alternate bscu_subsystem instances are in a failed state; the system shall enter an alternate operational state if the primary subsystem is failed while the alternate subsystem remains operational, or if both subsystems are operational but the select_alternate component is in a failed state; the system shall remain in a fully operational state only if both bscu_subsystem instances and the select_alternate component are in operational states. Concurrent loss of power to both external power inputs shall trigger a transition to the failed state for the generic, federated, and ima bscu implementations.

Deployment binding and scheduling rules shall be enforced per implementation variant to meet safety and temporal isolation requirements. For the bscu.federated implementation, the command and monitor processes of the primary bscu_subsystem instance shall be bound exclusively to the first central processing unit of the federated platform subcomponent, and the command and monitor processes of the alternate bscu_subsystem instance shall be bound exclusively to the second independent central processing unit of the federated platform subcomponent. Scheduling on federated platform processors shall enforce strict temporal separation between primary and alternate channel execution to prevent cross-channel fault propagation. For the bscu.ima implementation, the command process of the primary subsystem shall be bound exclusively to the first partition of the shared IMA platform central processing unit, the monitor process of the primary subsystem shall be bound exclusively to the second partition of the shared IMA central processing unit, the command process of the alternate subsystem shall be bound exclusively to the third partition of the shared IMA central processing unit, and the monitor process of the alternate subsystem shall be bound exclusively to the fourth partition of the shared IMA central processing unit. IMA partition scheduling shall enforce strict temporal and spatial isolation between all bound processes per ARINC 653 requirements to prevent fault propagation between processes sharing the same physical processor. Safety-related property constraints shall be applied per ARP4761 and EMV2 rules to meet certification requirements. The invalid report error event of the monitor process shall be classified as a minor hazard with a probable qualitative probability objective, describing a spurious monitor output that causes an invalid temporary switch to the alternate channel. The failed state of a single bscu_subsystem instance shall be classified as a major hazard with a probable qualitative probability objective, describing total failure of one BSCU channel, with a fixed occurrence probability of 3.3e-5 per operational period; this fault condition is noted to become catastrophic if both primary and alternate channels fail concurrently. The internal selection error event of the select_alternate component shall be classified as a hazardous hazard with an extremely improbable qualitative probability objective, describing an incorrect validity assessment that causes an uncommanded switch to the alternate channel without an actual primary channel fault, with a Poisson-distributed occurrence probability of 3.6e-6 per operational period, assigned a severity level of hazardous and likelihood level of extremely improbable per EMV2 property rules. Loss of a single external power supply to the bscu shall be classified as a hazardous hazard with an extremely improbable qualitative probability objective, while concurrent loss of both external power supplies shall be classified as a catastrophic hazard with an extremely improbable qualitative probability objective, describing permanent total loss of BSCU function. End-to-end latency for pedal input to command output delivery, and for validity fault detection to channel selection output delivery, shall be bounded to meet braking system response requirements, with no additional latency introduced by cross-partition or cross-processor communication paths beyond platform-enforced communication delays.

All data exchanged via component ports shall use strongly typed data definitions sourced exclusively from imported packages, with no implicit type conversions permitted at connection points. Pedal position values shall use the common::command.pedal data type, brake command values shall use the common::command.brake data type, skid command values shall use the common::command.skid data type, and all boolean validity status and channel selection flag values shall use the Base_Types::Boolean data type representing a binary true or false state. All power distribution connections shall use the common::power.generic bus type, which supports propagation of no-power error states to all connected components when the power supply is lost. All data port communications shall follow sampled port semantics, where only the most recently produced data value is delivered to the receiving component on each execution cycle, with no queuing of historical data values. Error propagation across all port and bus connections shall follow EMV2 rules, where only explicitly declared error types are transmitted across connection points, with error transformation logic defined per component error behavior specifications to map incoming error types to appropriate outgoing error types as required for fault impact analysis and FMEA reporting. All data type and bus definitions shall be reusable across other aircraft system models, with no model-specific modifications made to imported type or bus definitions within the bscu package.
