The system shall define an independent public shared package named common, with all internal elements declared as publicly accessible. This package holds no dependencies on external AADL packages, and hosts globally reusable bus types, bus implementations, data types, and data implementations. No functional components including processors, processes, threads, or devices shall be defined within this package. All elements contained in the package have no cross-package reference requirements, and complete the binding between type declarations and corresponding implementations entirely within the public scope of the common package.

The system shall define three distinct bus components within the common package, with no externally exposed functional interaction ports or internal subcomponent structure specified at the bus type level. The first bus component is the power bus type, designed to support system-wide power transmission, paired with a generic bus implementation identified as power.generic. This implementation includes no additional attribute configurations or internal connection logic, and is applicable to universal power delivery scenarios. The second bus component is the pwm bus type, designed to support system-wide pulse width modulation signal transmission, paired with a generic bus implementation identified as pwm.generic. This implementation includes no additional attribute configurations or internal connection logic, and is applicable to universal PWM control signal delivery scenarios. The third bus component is the pressure bus type, designed to carry pressure signals sent and received between connected devices, pump units and other system nodes, paired with a standard bus implementation identified as pressure.i. This implementation includes no additional attribute configurations or internal connection logic, and is applicable to cross-component pressure signal interaction scenarios. The system shall define one base data component named command within the common package, which acts as the parent type for all concrete control instruction data, with no fixed internal data field constraints specified at the data type level. The command data type is paired with four scenario-specific concrete data implementations, all of which contain no additional internal data field extensions or nested substructures. The first data implementation is command.brake, which carries brake control instruction payloads. The second data implementation is command.skid, which carries skid control instruction payloads. The third data implementation is command.pedal, which carries pedal operation instruction payloads. The fourth data implementation is command.announce, which carries system announcement and prompt instruction payloads.

As a foundational resource definition package, the common package does not define independent end-to-end data flow paths natively. All bus types and implementations defined in the package provide logical and physical bearer channels for cross-component energy, signal, and data transmission in upper-level system architecture. All data types and implementations defined in the package provide standardized format specifications for information payloads exchanged between distributed system components. When upper-level systems construct concrete data flow links, they may directly bind the corresponding bus implementation as the transmission carrier, and instantiate the corresponding data implementation as the transmitted interaction payload.

All bus and data elements defined in the common package are not bound to dedicated timing scheduling rules, and are not configured with fixed end-to-end or per-hop latency constraint parameters. All timing-related attributes, scheduling execution policies, and latency performance indicators shall be configured by upper-level functional components that reference these foundational resources, in accordance with specific application scenario requirements. The foundational resources in the common package maintain a generic, unbound state, and impose no mandatory restrictions on the scheduling strategies or latency metrics adopted by upper-level applications.

For public data type definition, a hierarchical structure consisting of a base type and scenario-specific implementations shall be applied. The base command type defines the classification category for general instruction-class data, while each scenario-specific data implementation corresponds to a concrete business-domain instruction type. Data implementations do not predefine fixed field lengths, encoding rules, or data resolution parameters, to reserve sufficient extension space for upper-level application adaptation across different deployment contexts. For public communication bus definition, a hierarchical structure consisting of a bus type and corresponding general or standard implementation shall be applied. Each bus type explicitly defines its applicable scenario: the power bus supports power energy transmission scenarios, the pwm bus supports pulse width modulation control signal transmission scenarios, and the pressure bus supports pressure measurement and control signal transmission scenarios. Each bus implementation does not predefine hardware-specific parameters such as bandwidth, transmission rate, or electrical interface characteristics, to reserve sufficient extension space for upper-level adaptation across different hardware platforms. All bus implementations are generic foundational units with no embedded internal logic, and may be directly bound and referenced by bus access ports of upper-level components.
