The system shall define a publicly accessible AADL package named WBS_Proofs to serve as the dedicated namespace for all wheel brake system geometry conformance proof constructs. The package shall not declare import dependencies on any external AADL packages, as all logic contained within the package is fully self-contained. The public section of the package shall include a single package-level Resolute annex subclause to host all executable assurance claim definitions, helper functions, and external analysis invocation logic. No additional top-level AADL declarations including component types, component implementations, data types, or bus definitions shall be placed directly in the public package section outside the Resolute annex subclause.

Within the package-level Resolute annex, three parameterless top-level assurance claims shall be defined as the externally accessible validation entry points for geometry conformance checks. The first entry point, identified as contain_two_bscu, shall encapsulate the check for required BSCU components in the referenced system geometry model. The second entry point, identified as contain_two_selector_valve, shall encapsulate the check for required selector valve components in the referenced system geometry model. The third entry point, identified as contain_two_power_supply, shall encapsulate the check for required electrical power supply components in the referenced system geometry model. A single internal reusable helper function named contains_geometry shall be defined within the same Resolute annex scope to support execution of the three top-level claims, with a formal input interface accepting three positional parameters: a string value specifying the full file system path of the target geometry model file, a string value specifying the exact component name to search for within the geometry model, and an integer value specifying the minimum required count of components matching the target name. The contains_geometry helper function shall have scope restricted to invocation by constructs within the same Resolute annex, and shall not be exposed as an external validation entry point for referencing models. Each top-level claim shall invoke the contains_geometry helper with fixed hardcoded parameter values: the contain_two_bscu claim shall pass the file path value "C:\\jjc.stp", component name value "BSCU", and required count value of 1; the contain_two_selector_valve claim shall pass the file path value "C:\\jjc.stp", component name value "SELECTOR VALVE", and required count value of 2; the contain_two_power_supply claim shall pass the file path value "C:\\jjc.stp", component name value "ELECTRICAL POWER SUPPLY", and required count value of 2.

During execution of architecture validation activities, data shall flow along a fixed linear path for each top-level assurance claim. When a top-level claim is triggered by the Resolute assurance framework, the fixed parameter values hardcoded in the claim definition shall be passed directly as input arguments to the internal contains_geometry helper function, with no intermediate data transformation or persistent storage applied to the parameter values. Upon receiving the input parameters, the contains_geometry helper function shall pass the three received values as sequential positional arguments to the external ngrep geometry analysis utility. The ngrep utility shall access the geometry file at the specified file path, scan the file content to count elements matching the provided component name, compare the counted value against the required minimum count, and generate a boolean pass or fail result. This result shall be passed directly back from the ngrep utility to the contains_geometry helper function, which propagates the result unchanged to the calling top-level claim. The top-level claim shall then return the final boolean result to the Resolute framework to indicate whether the geometry conformance requirement is satisfied. No branching data paths, feedback loops, or parallel data processing steps shall be included in the validation logic flow.

No runtime task scheduling configurations, execution priority assignments, periodic trigger rules, event-triggered activation logic, or hard end-to-end latency constraints shall be defined within the WBS_Proofs package. All logic contained in the package supports offline architecture verification activities that execute outside the operational runtime context of the deployed wheel brake system, and thus is not subject to the real-time scheduling rules applied to runtime system components. Invocation of the top-level assurance claims and supporting helper functions shall occur synchronously when triggered by a user-initiated or automated architecture validation workflow. No mandatory upper bound shall be imposed on the execution duration of the ngrep analysis utility or the associated Resolute function calls, as execution time may vary based on host system performance and geometry file size.

All parameter values exchanged between Resolute functions within the package, and between the contains_geometry helper function and the external ngrep analysis utility, shall use built-in primitive data types natively supported by the Resolute annex language. String data type shall be used for all values representing file system paths and component name identifiers, and integer data type shall be used for all values representing minimum required component counts. No custom user-defined AADL data types shall be declared within the WBS_Proofs package, as all data exchange uses the supported primitive types. No AADL bus, virtual bus, bus access interface, or formal communication protocol definition shall be included in the WBS_Proofs package, as the contained validation logic does not model runtime inter-component communication paths for the deployed wheel brake system. Data exchange between Resolute functions and the external ngrep utility shall use direct in-memory parameter passing with positional argument ordering, and shall not require dedicated communication bus infrastructure, message encoding rules, or transport layer protocols.
