A public AADL package named communication shall be defined to encapsulate modeling elements associated with system annunciation functionality. The communication package shall declare explicit import dependencies on three external packages: the common package for shared public data type definitions, the EMV2 package for standardized error modeling annex support, and the ARP4761 package for aviation system safety and hazard analysis property support. The communication package shall not contain nested subpackages, and shall define a single device type named annunciation as its core functional element. The annunciation device is specified to abstract the system’s annunciation capability at an abstraction level sufficient to represent communication error scenarios that cause total loss of annunciation function, with modeling logic aligned to the fault tree error injection approach described in ARP4761 document page 199, figure L3. Overly sophisticated internal logic of physical annunciation hardware shall not be modeled at this abstraction level, as the core modeling purpose of the device is to represent an error source that propagates fault effects to the top-level system. A single device implementation identified as i shall be provided for the annunciation device type, and this implementation shall contain no internal subcomponents, internal connections, or standalone annex definitions, representing the minimal structural implementation of the annunciation device.

The annunciation device type shall define exactly one external interaction feature, which is an output data port named information. No input data ports, event ports, event data ports, bus access points, subprogram access points, or parameter connection points shall be defined for the annunciation device type. The annunciation.i implementation shall not define any additional external features beyond those inherited from the annunciation device type, and shall not expose internal subcomponent interfaces to the external environment. For error propagation interfaces, the annunciation device shall define an outbound error propagation path bound to the information output port, where the only permitted propagated error type is the NoService loss-of-service error.

Under normal operational conditions, the annunciation device acts as the originating source of annunciation information, generating and transmitting annunciation data conforming to the bound port data type outwards through the information output port. The device shall not accept incoming data from external components as input to generate its output annunciation content. A designated error flow labeled f1 shall be defined for the device, which treats the information port as an error source point that propagates NoService errors outwards to connected external components. When the device enters a failed state, normal annunciation data transmission on the information port shall cease, and the NoService error shall be transmitted along the same port connection path to connected upstream system elements, forming a complete fault propagation path for loss of annunciation capability across the device’s system boundary.

The annunciation device shall implement a two-state error behavior model for operational state tracking. The two defined states are the Operational state representing normal functional operation, and the Failed state representing total loss of annunciation function, with the device initializing in the Operational state on system startup. A single internal error event named LossAnnunciation shall be defined as the sole trigger for functional state transition. A single state transition labeled t1 shall be specified, which moves the device from the Operational state to the Failed state immediately upon occurrence of the LossAnnunciation event, with no intermediate states or guard conditions applied to the transition. A single error propagation rule labeled p1 shall be defined, which triggers unconditionally when the device is in the Failed state to propagate the NoService error to the information output port, with no additional trigger events or conditional checks applied to this propagation. The LossAnnunciation error event shall be assigned an occurrence distribution property per EMV2 specification, set to a fixed probability distribution with a probability value of 1.00. The LossAnnunciation event shall be associated with ARP4761 hazard properties as follows: the hazard cross-reference shall point to content from AIR6110 and ARP4761 corresponding to ARP4761 page 199, figure 3, the associated failure mode shall be Loss of Annunciation, the hazard shall apply to all operational phases of the system, the hazard description shall state that the system cannot annunciate errors, the failure condition classification shall be set to Catastrophic, the qualitative probability objective for the hazard shall be set to ExtremelyImprobable, and no additional comment text shall be attached to the hazard entry. No explicit periodic task scheduling rules, execution offset constraints, or end-to-end communication latency limits shall be defined for the annunciation device or its implementation, as the device operates as an event-driven source of data and fault effects without scheduled periodic execution requirements.

The communication package shall not define any custom bus types, bus implementations, or native data types within its scope. All data transmitted across the information port shall use the pre-defined announce data type located under the command namespace of the imported common package, with no local modification or extension to this data type permitted within the communication package. All error modeling types and behavior constructs used in the device error model shall be imported from the pre-defined error_library, specifically utilizing the simple error behavior set from the error library, with no custom error types or error behavior states defined locally in the communication package. All port-based communication for the annunciation device shall use the standard AADL data port communication mechanism, with no dedicated custom communication bus specified for annunciation data transmission at this modeling abstraction level.
