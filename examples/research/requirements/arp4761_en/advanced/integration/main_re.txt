The top-level modeling package shall be defined as integration::main, with all contained model elements declared within the public section of the package. The package shall declare explicit import dependencies on two external packages, functional::main and impl::wbs, to resolve all references to component types, component implementations, and associated properties defined in those packages. The package shall define a top-level system type named main, which acts as the root component of the integrated aircraft system deployment. A corresponding system implementation named main.impl shall be defined for the main system type to represent the complete integrated deployment configuration. The main.impl implementation shall instantiate two first-level subcomponents. The first subcomponent shall be named functional, instantiated from the basic implementation of the Aircraft system defined in the functional::main package. The second subcomponent shall be named wbs_impl, instantiated from the ima implementation of the wbs system defined in the impl::wbs package. The integration::main package shall not define additional component types, data types, bus types, or property sets beyond the main system type and its main.impl implementation, with all subcomponent references resolved exclusively from imported dependent packages. The EMV2 error behavior annex attached to main.impl shall declare dependencies on the WBSMappingErrorLib library, importing the FunctionToImplementation error type equivalence definition and the Basic error behavior definition to support composite error state propagation modeling.

The top-level main system type shall not define any externally exposed interaction ports, including data ports, event ports, and event data ports, establishing a closed integration layer boundary with no direct external interfaces defined at this level. The main.impl implementation shall define explicit Actual_Processor_Binding properties to map functional elements to their supporting physical runtime components, following binding propagation rules that require physical components to explicitly declare binding propagation attributes, while functional elements reference their associated runtime components via the processor binding property. The alert functional element contained within the functional subcomponent shall be bound to the bscu processor component contained within the wbs_impl subcomponent. The DecelerateWheels functional element contained within the decelerate functional module of the functional subcomponent shall be bound to the wbs_impl subsystem as a whole. The hydraulic functional element contained within the functional subcomponent shall be simultaneously bound to three physical components under the wbs_impl subcomponent: the blue_pump component, the green_pump component, and the accumulator component. The electrical functional element contained within the functional subcomponent shall be simultaneously bound to three power-related elements under the wbs_impl subcomponent: the power subsystem, the battery1 component nested under the power subsystem, and the battery2 component nested under the power subsystem. No functional element under the functional subcomponent shall remain unbound to a physical runtime element from the wbs_impl subcomponent. The composite error behavior logic defined for main.impl shall implement a direct failure propagation rule, where the top-level main system transitions to the Failed state immediately when the functional subcomponent enters the Failed state, with no intermediate error states or additional transition conditions specified for this failure path.

The main.impl integration implementation shall not define explicit port connections, including data connections, event connections, and event data connections, between the functional subcomponent and the wbs_impl subcomponent. All data exchange, service invocation, and state transmission interactions between functional elements and physical implementation elements shall be carried through the established processor binding relationships, with each functional element routing all runtime interaction traffic exclusively to its bound set of physical runtime elements. No data flow path shall be established between a functional element and a physical element that is not included in its declared processor binding set. All internal data flows and port connections within the functional subcomponent and within the wbs_impl subcomponent shall retain their original definitions from their respective source packages, with no connection rerouting, addition, or modification introduced at the integration layer.

The integration layer shall not define, override, or extend any timing, scheduling, or latency properties for contained subcomponents, including but not limited to task dispatch periods, worst-case execution time budgets, scheduling priorities, end-to-end flow latency budgets, and communication transmission delay values. All timing and scheduling rules for functional and physical components shall be inherited directly from the native definitions in the functional::main and impl::wbs dependent packages. The established processor binding relationships shall not alter the native scheduling parameters, priority assignments, or latency guarantees of the bound functional and physical elements. No additional timing constraints shall be imposed at the integration layer that would conflict with constraints defined in the original source packages of the subcomponents.

The integration::main package shall not define any custom data types within its scope. All data types used for functional interaction, state transmission, parameter passing, and fault signaling across the integrated system shall be reused exclusively from pre-defined data types in the functional::main and impl::wbs dependent packages, with no new data type definitions introduced at the integration layer. The integration::main package shall not define any custom bus types or bus instances within its scope. All communication buses used for inter-component and intra-component data transmission shall be reused exclusively from pre-defined bus implementations in the two imported dependent packages. The integration layer shall not modify native bus attributes including communication protocol specifications, available bandwidth, transmission latency, and fault handling mechanisms for any reused bus instance.
