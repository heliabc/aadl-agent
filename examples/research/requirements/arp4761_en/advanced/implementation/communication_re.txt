A public AADL package named impl::communication shall be defined, with explicit import dependencies on three external packages: the common package that provides shared public data type definitions, the EMV2 standard annex package that supplies formal error modeling constructs, and the ARP4761 standard annex package that provides aviation system safety assessment constructs. This package shall encapsulate components associated with system annunciation communication functions, and shall not contain nested sub-packages at the current abstraction level. A top-level device component typed as annunciation shall be declared within the package, alongside its corresponding device implementation identified as annunciation.i. The annunciation.i implementation shall maintain an empty internal structure at the current abstraction level, with no declared subcomponents, internal connections, or internal execution logic, serving only as a concrete instantiation carrier for the annunciation device type.

The annunciation device type shall define a single outward-facing unidirectional out data port named information as its only external feature, with no additional input ports, event ports, event data ports, bus access points, or subprogram access points declared on the device type. The information port shall be typed to carry data instances matching the announce data type defined under the command namespace of the imported common package. The annunciation.i device implementation shall not define additional external interfaces beyond those inherited from the annunciation device type, shall not declare internal private interfaces, and shall not define port mappings for non-existent internal subcomponents. An EMV2 annex shall be attached to the annunciation device type to formalize its error behavior, which shall import error type definitions from the WBSImplementationErrorLib error library, and reference the Twostate error behavior state machine definition from that same library to structure the device’s dual-state error model. Per the EMV2 error propagation configuration, the information out port shall support outward error propagation, allowing NoService category errors to be transmitted out of the device through this port.

The logical data and error flow associated with the annunciation device shall follow paths aligned with device operational state. When the device operates in a non-faulted state, valid annunciation command data conforming to the common::command.announce type specification shall be transmitted out of the device through the information port to connected downstream components. When the device enters a faulted state, no valid annunciation data shall be transmitted through the information port, and a NoService error state shall be propagated outward through the port to indicate total loss of annunciation capability; this fault represents a communication-related error source that propagates to the top-level system for inclusion in system-level fault tree analysis aligned with ARP4761 guidance, at a level of abstraction sufficient to represent annunciation capability loss without requiring detailed lower-level communication mechanism modeling. A dedicated error flow path identified as f1 shall be defined within the EMV2 annex to mark the NoService error present on the information port as an error source originating directly from the annunciation device itself, with no cross-subcomponent error transfer paths defined given the empty internal structure of the annunciation.i implementation.

At the current abstraction level, no periodic scheduling rules, execution time budgets, data transmission latency constraints, or hardware binding rules for processors, memory, or buses shall be defined for the annunciation device or its annunciation.i implementation. The device’s error behavior state machine shall follow explicit transition and propagation rules: the device shall initialize in the Operational working state as defined by the referenced Twostate behavior model, and shall transition to the Failed state via transition t1 immediately when the internal LossAnnunciation error event is triggered. When the device resides in the Failed state, it shall unconditionally propagate a NoService error to the information port via propagation rule p1, with no additional triggering events or guard conditions required for this error propagation. The LossAnnunciation error event shall be assigned an EMV2 OccurrenceDistribution property, following a Fixed distribution type with a probability value of 1.00. Per ARP4761 safety assessment requirements, the LossAnnunciation error event shall be associated with a formal hazard record: the hazard shall carry a cross-reference to AIR6110 and ARP4761 documentation, specifically aligned with the fault tree construct for annunciation loss defined on page 199, figure L.3 of the ARP4761 standard, the failure condition shall be titled "Loss of Annunciation", the hazard shall apply across all system operational phases, the hazard effect shall be described as total inability of the system to annunciate error conditions, the failure condition classification shall be set to Catastrophic, the associated qualitative probability objective shall be set to Extremely Improbable, and no additional comment text shall be attached to the hazard record.

The impl::communication package shall not define custom native data types for inter-component communication, and shall instead reuse the pre-defined common::command.announce data type from the imported common package for all payload data transmitted through the information port. All data and error transfer associated with the device shall be modeled via abstract data port connections at the current abstraction level. The package shall not define dedicated physical bus components, virtual bus components, or custom bus protocol specifications, and no explicit bus binding properties shall be assigned to the information port at this level of design abstraction, as the port serves only as an abstract representation of internal system communication for annunciation data.
