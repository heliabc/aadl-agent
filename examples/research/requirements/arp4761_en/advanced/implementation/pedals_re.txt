The system shall define a publicly accessible AADL package named impl::pedals to encapsulate all model elements related to the pedal input unit. This package shall declare explicit import dependencies on two external packages: the common package to access shared command data type definitions, and the ARP4761 package to access standardized aviation safety assessment property sets. The impl::pedals package shall contain one top-level system component type named pedals, which represents a stub representation of the pedal input hardware, and one corresponding system implementation instance named pedals.generic that realizes the pedals system type.

The pedals system type shall expose two external outbound data port features for inter-component communication. The first port, designated signal1, shall be defined as an out data port typed to the common::command.pedal data type. The second port, designated signal2, shall be defined as an out data port also typed to the common::command.pedal data type. Both outbound ports shall support declared outbound propagation of the NoService error state to enable formal safety analysis. The pedals.generic system implementation shall not define any internal subcomponents, internal connection paths, private features, or subcomponent-level property assignments, consistent with its purpose as a minimal stub component.

The pedals component shall operate as an originating source of pedal command data for downstream aircraft braking system components. During normal operation, pedal position command data generated by the pedal unit shall be transmitted outward through both signal1 and signal2 data ports to connected receiving components, with no inbound data or event flows defined for the component. For safety-related error flows, the component shall define two distinct error source paths: the first error flow, identified as f1, shall treat the signal1 port as an originating source of the NoService error state, and the second error flow, identified as f2, shall treat the signal2 port as an originating source of the NoService error state, with no internal error propagation waypoints defined between component internal states and the port error outputs.

The pedals component shall implement error behavior aligned with the Twostate behavior definition sourced from the WBSImplementationErrorLib library, and shall reference error type definitions from the same WBSImplementationErrorLib library for error state and event specification. The component shall define a single internal error event named InternalFault that triggers operational state transitions. The component shall default to the Operational state during normal function, where valid pedal command data is transmitted across both output ports. Upon occurrence of the InternalFault event, the component shall execute an immediate state transition from the Operational state to the Failed state. When in the Failed state, the component shall unconditionally propagate the NoService error state out through both signal1 and signal2 ports, with no additional guard conditions or processing delay applied to this error propagation. The NoService error condition present on both signal1 and signal2 ports shall be mapped to an ARP4761 hazard entry classified as Catastrophic, with a qualitative probability objective of ExtremelyImprobable. The hazard shall be documented as a total loss of pedal signal input that prevents the BSCU from generating valid brake control outputs, with an associated comment noting the condition reaches critical severity in the event of dual power supply loss. All hazard cross-reference identifiers, applicable operational flight phases, and associated detailed reference fields shall be marked as TBD for subsequent design refinement. No explicit periodic scheduling rules, execution deadline constraints, data transmission latency limits, or clock synchronization requirements shall be defined for the pedals.generic stub implementation, with such timing parameters reserved for definition in future detailed, non-stub implementations of the pedal component.

All data transmitted across the signal1 and signal2 output ports shall strictly conform to the structure and semantics of the common::command.pedal data type defined in the imported common package. No custom data type definitions shall be declared within the impl::pedals package, as all interface data types are sourced from shared common definitions. No dedicated communication bus components, bus access features, or protocol binding rules shall be defined within the impl::pedals package, as the generic stub implementation uses unbound direct data port interfaces for signal transmission without explicit underlying communication network specification.
