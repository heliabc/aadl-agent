The module set for the valve domain is encapsulated within the impl::valves package, which declares explicit dependencies on two external public packages: the base_types package for fundamental data type definitions, and the common package for shared bus and skid command data type definitions. All component type and implementation definitions are contained in the public section of the package to support unconstrained external reference. The component hierarchy follows a single-inheritance structure to reuse common interface and behavior definitions. A base generic valve system type is defined as the common parent for three specialized valve variants: the generic_pwm_input valve with added PWM control input, the boolean_shutoff valve with added binary shutoff control, and the cmd_shutoff valve with added skid command shutoff control. A base selector system type is defined as the common parent for two specialized pressure selector variants: the selector_basic unit with single consolidated pressure output, and the selector_detailed unit with dual independent channel pressure outputs. System implementation definitions are provided for three of the system types: the base generic valve (generic.i), the PWM-input generic valve (generic_pwm_input.i), and the base selector (selector.i). All three existing implementations contain no internal subcomponents, port groups, connection structures, or internal behavior specifications. The boolean_shutoff valve, cmd_shutoff valve, selector_basic, and selector_detailed system types are defined as formal type specifications only, with no corresponding implementation provided in the current package version.

Each component defines explicit external interfaces aligned with its functional role, with standardized error propagation and behavior specifications defined via the EMV2 annex. All error type definitions referenced across components are sourced from the external WBSImplementationErrorLib; components that define state-based error behavior additionally reference the two-state (Operational/Failed) behavior model from the same library. The base generic valve exposes two bus access ports: an input port with requires bus access semantics to connect to an upstream pressure bus, and an output port with provides bus access semantics to expose pressure output to downstream components. Its error propagation specification defines that the input port may receive incoming NoService errors, the output port may propagate outgoing NoService errors, and a direct error flow path carries NoService errors from the input port to the output port. The generic.i implementation of the base valve adds no additional interfaces or internal structure. The generic_pwm_input valve inherits all interfaces and error propagation rules from the base generic valve, and adds one additional requires bus access port named input_pwm to connect to a generic PWM control bus, with no supplementary error propagation or behavior rules; its generic_pwm_input.i implementation contains no extra internal structure or interface definitions. The boolean_shutoff valve inherits all interfaces and error propagation rules from the base generic valve, and adds one additional input data port named boolean_input typed to Base_Types::Boolean to receive binary shutoff control signals, with no supplementary error propagation or behavior rules, and no provided implementation in the current package. The cmd_shutoff valve inherits all interfaces and error propagation rules from the base generic valve, and adds one additional input data port named cmd_input typed to common::command.skid to receive skid-related shutoff commands. Its error propagation specification defines that the cmd_input port may receive incoming NoValue errors, an error flow path maps NoValue errors on cmd_input to NoService errors on the pressure output port, and the pressure output port may act as an originating source of NoService errors. Its component error behavior, based on the two-state model, defines an initial Operational state, with transitions to a Failed state triggered by either NoValue errors on the cmd_input port or NoService errors on the pressure input port; when in the Failed state, the component unconditionally propagates NoService errors out of the pressure output port. No implementation is provided for the cmd_shutoff valve in the current package. The base selector system exposes three requires bus access ports for pressure inputs: accumulator_input to connect to the accumulator pressure bus, green_input to connect to the green hydraulic system pressure bus, and blue_input to connect to the blue hydraulic system pressure bus. It also exposes three input data ports: select_alternate typed to Base_Types::Boolean to receive alternate source selection control signals, cmd_nor typed to common::command.skid to receive normal channel control commands, and cmd_alt typed to common::command.skid to receive alternate channel control commands. Its error propagation specification defines that the three control data ports may receive incoming NoValue errors, the three pressure input bus ports may receive incoming NoService errors, and all NoValue errors arriving on the three control data ports are treated as error sinks that terminate within the component without outward propagation. The selector.i implementation of the base selector adds no additional interfaces or internal structure. The selector_basic variant inherits all interfaces and error propagation rules from the base selector, and adds one additional provides bus access port named output to deliver selected pressure output to downstream components. Its error propagation specification defines that the output port may propagate outgoing NoService errors, with direct error flow paths carrying NoService errors from each of the three pressure input ports to the single output port. No implementation is provided for selector_basic in the current package. The selector_detailed variant inherits all interfaces and error propagation rules from the base selector, and adds two additional provides bus access ports: green_output to deliver pressure for the green hydraulic channel, and blue_output to deliver pressure for the blue hydraulic channel. Its error propagation specification defines that both output ports may propagate outgoing NoService errors, with mapped error flow paths as follows: NoService errors on green_input propagate to green_output, NoService errors on blue_input propagate to blue_output, NoService errors on accumulator_input propagate to both green_output and blue_output, NoValue errors on cmd_alt propagate to blue_output as NoService errors, NoValue errors on cmd_nor propagate to green_output as NoService errors, and NoValue errors on select_alternate propagate to both green_output and blue_output as NoService errors. Its component error behavior, based on the two-state model, defines an initial Operational state, with transitions to a Failed state triggered by NoValue errors on the select_alternate, cmd_alt, or cmd_nor ports; when in the Failed state, the component unconditionally propagates NoService errors out of both green_output and blue_output ports. No implementation is provided for selector_detailed in the current package.

Functional data flow across all components follows the expected signal paths of a hydraulic valve control system. For all valve types derived from the base generic valve, the core functional flow carries pressure signals from the upstream pressure bus connected to the input port, through the valve’s internal regulation and shutoff logic, to the downstream pressure bus exposed via the output port. The generic_pwm_input valve supplements this core pressure flow with PWM control signals received via the input_pwm bus port, which are used to modulate the valve’s opening level and pressure output. The boolean_shutoff valve supplements the core pressure flow with binary shutoff signals received via the boolean_input data port, which trigger a full block of the pressure output path when the shutoff condition is asserted. The cmd_shutoff valve supplements the core pressure flow with skid command signals received via the cmd_input data port, which trigger a full block of the pressure output path when a valid shutoff command is received. For selector components, the base selector accepts three independent pressure inputs and three control inputs as the complete signal set for pressure source selection logic. The selector_basic variant uses the received alternate selection signal and channel commands to select one of the three input pressure sources, and routes the selected pressure signal to the single output pressure bus port for downstream consumption. The selector_detailed variant uses the received alternate selection signal and channel commands to independently select pressure sources for the green and blue hydraulic channels, routing processed pressure for the green channel to the green_output port and processed pressure for the blue channel to the blue_output port. Error flow follows explicitly defined propagation paths aligned with expected failure modes. For the base generic valve, NoService errors on the pressure input pass directly through to the pressure output with no masking or transformation. For the cmd_shutoff valve, NoValue errors on the command input and NoService errors on the pressure input both trigger a component failure state that generates NoService errors on the pressure output, and the output may also generate NoService errors as an internal fault source. For the base selector, all NoValue errors on control input ports are contained within the component with no outward propagation, regardless of component state. For the selector_basic variant, NoService errors on any of the three pressure inputs pass directly through to the single pressure output with no masking. For the selector_detailed variant, NoService errors on the dedicated green and blue pressure inputs pass directly to their corresponding channel outputs, NoService errors on the accumulator input propagate to both channel outputs, NoValue errors on control inputs either propagate directly to associated outputs as NoService errors or trigger a global component failure that propagates NoService errors to both channel outputs simultaneously.

No internal threads, processes, scheduled subcomponents, or execution timeline constructs are defined in any of the current system type specifications or existing implementations, so no internal scheduling priority, dispatch period, execution time, deadline, or jitter constraints are specified for component internal logic. All defined error propagation paths follow zero-delay instantaneous propagation semantics with no added latency or buffering requirements. Communication across all data ports and bus access ports carries no explicit custom latency constraints, and all signal transmission timings align with the native timing specifications of the connected external buses and imported data types. No end-to-end latency budgets are defined for pressure or control signal paths across any of the valve or selector components in the current package.

All data types used by components in the package are imported from external packages, with no custom data type definitions contained within the impl::valves package. Boolean control signals for shutoff and source selection use the Boolean type defined in the base_types package, while skid command signals for channel control use the command.skid type defined in the common package. All data ports use standard unqueued AADL data port communication semantics with no custom data representation, encoding, endianness, or refresh rate rules specified at the component level. All pressure signal interactions use the pressure.i bus defined in the common package, while all PWM control interactions use the pwm.generic bus defined in the common package. Bus connections follow standard requires/provides access semantics consistent with bidirectional client-server interaction models, where pressure buses carry hydraulic pressure measurement and actuation signals or their equivalent digital representations, and PWM buses carry pulse-width modulated valve actuation control signals. No custom bus protocol, baud rate, electrical characteristic, data framing, or access arbitration rules are defined within the package; components only expose access points to connect to externally defined buses without modifying inherent bus properties or behavior.
