The system shall define a public AADL package named impl::pump. This package shall declare explicit import dependencies on three external modeling packages, including the common shared definition package, the ARP4761 safety standard property package, and the EMV2 error modeling annex package. The impl::pump package shall contain one top-level system type definition named pump, and one matching system implementation definition named pump.i. The pump.i system implementation shall not include internal subcomponent declarations, internal connection definitions, or internal subcomponent binding configurations in the current modeling scope.

The pump system type shall define its external functional interface as a single provided bus access feature named pressure_output. The pump system shall define two outward-facing error propagation points as part of its error modeling interface. The first outward error propagation point is named bindings, which is associated with component implementation binding layers, and shall support propagation of all implementation-level error categories. The second outward error propagation point is mapped directly to the pressure_output functional feature, and shall support propagation of service loss errors. The pump system shall define two top-level error source flow specifications for its error interface: the first error source flow, named nopressure, shall originate at the pressure_output propagation point and carry service loss errors; the second error source flow, named nopressurefunc, shall originate at the bindings propagation point and carry all implementation-level error categories. The pump.i system implementation shall not define any internal private interfaces, as no internal subcomponents are present in the implementation structure.

For functional service flow, the pump component shall provide accessible pressure bus service to external connected components through the pressure_output provided bus access port during normal operation. For error propagation flow, when the component operates without fault, no functional error shall be passed to external components through the pressure_output port, and no binding layer error shall be propagated through the bindings point. When the component encounters an internal hydraulic fault, corresponding error signals shall propagate outward through the two defined error propagation points to reach connected system components and platform binding layers, without blocking or internal error consumption within the pump component. No internal data transformation or routing logic shall be defined in the pump.i implementation, as the component operates as a standalone service provider with no internal subcomponent data exchange paths.

The pump component shall implement a two-state error behavior state machine aligned with the Twostate behavior definition imported from the WBSImplementationErrorLib error library. The component shall initialize to the Operational state upon system power-up and normal startup. The component shall define one internal error event named HydraulicError, which triggers an immediate state transition from the Operational state to the Failed state, with no intermediate wait states or transitional processing steps permitted. No recovery transition from the Failed state back to the Operational state shall be implemented in the current model. When the component remains in the Operational state, it shall continuously propagate a NoError status through the pressure_output error propagation point with no added propagation delay. When the component enters the Failed state, it shall immediately propagate a NoService error through the pressure_output point and an AnyImplementationError through the bindings point, with zero added processing delay for error propagation per the model definition. The HydraulicError event and the associated NoService error propagation on the pressure_output port shall follow a Poisson occurrence distribution, with a fixed probability value of 2.5e-5 per defined operational exposure interval. The HydraulicError event shall be associated with a hazard assessment per ARP4761 requirements, with a cross-reference to ARP4761 page 275 figure L9, a failure description of Hydraulic Error on a pump, applicable operational phases marked as to be determined, a hazard description of Loss of one pump, a failure condition classification of Major, a qualitative probability objective of Probable, and an associated comment noting that a Major hazard condition arises only when both pumps in the overall system experience loss of function.

The pressure_output provided bus access feature shall be bound to the common::pressure.i bus definition imported from the common package, which defines the physical and logical communication rules for pressure-related signal transmission between the pump and connected external components. All error types used in the pump error model shall be imported from the WBSImplementationErrorLib error type library, including the NoService error type for functional service loss, the AnyImplementationError type for binding layer implementation faults, and the NoError type for normal fault-free operation. No custom local data type or bus type definitions shall be declared within the impl::pump package, as all interface and communication type definitions are sourced from imported external packages.
