A standalone public AADL package named WBSImplementationErrorLib shall be constructed to serve as the dedicated error model definition library for the implementation layer of the wheel brake system. Only the standard EMV2 error model annex shall be embedded within the public scope of the package, and no other categories of AADL component structures shall be defined in the package. The error behavior definition units contained in the EMV2 annex of the package shall import the functional-layer error types defined in the separate external package WBSFunctionalErrorLib as a dependency. No other cross-package dependencies or circular package dependencies shall exist, and all definition elements within the package shall be publicly accessible for reference by other modeling packages associated with the wheel brake system.

This package functions as a static modeling metadata repository, and does not define runtime-capable components including hardware, software, process, or thread elements. Accordingly, no runtime interaction ports, bus access points, data access points, service provision points, or service request interfaces shall be configured. All error type and error behavior state machine definitions within the package shall be exposed as publicly referenceable modeling elements without access permission restrictions, for direct invocation when other components bind error models. No private internal interaction interfaces shall be defined in the package, and all definition elements shall reside at the public visibility level.

This package contains no definitions of runtime component instances, communication links, or data interaction paths, so no runtime cross-component data transmission or event-triggered data flow logic shall be specified. All elements within the package are static structural definitions for the modeling phase, and shall not participate in the data flow process during system runtime.

This package does not define schedulable runtime entities, communication transmission links, or temporal trigger logic. Accordingly, no temporal-related constraints including periodic scheduling rules, execution delay limits, communication transmission delay requirements, deadline restrictions, or priority configurations shall be specified. All error behavior state machines shall only describe the static structure of component state transition logic, and shall not be bound to specific temporal trigger conditions.

No communication bus types, bus instances, or associated bus access protocols shall be defined in the package. A structured error type system shall be defined within the EMV2 annex. Top-level independent error types with no parent type include AnyImplementationError, HydraulicLossBlue, HydraulicLossGreen, HydraulicLossComponents, SoftwareFailure, and HardwareFailure. AnyImplementationError serves as the abstract base type for all core implementation-layer functional errors of the wheel brake system, and relevant wheel brake function error types shall inherit directly or indirectly from this base type. The first-level subtypes directly inheriting from AnyImplementationError include NoService, TotalWBLoss, PartialSymmetricalWBLoss, AssymetricalWBLoss, and InadvertentWB. Among the second-level derived types, NoService acts as the intermediate base type for service-missing errors, and further derives two subtypes: NoValue and NoPower, which correspond to the failure scenarios of missing value output and missing power supply respectively. TotalWBLoss acts as the intermediate base type for total wheel brake loss errors, and further derives two subtypes: TotalWBLossAnunciated and TotalWBLossUnanunciated, which correspond to total wheel brake loss failure scenarios with active alarm notification and without active alarm notification respectively. PartialSymmetricalWBLoss acts as the intermediate base type for symmetrical partial wheel brake loss errors, and further derives two subtypes: PartialSymmetricalWBLossAnunciated and PartialSymmetricalWBLossUnanunciated, which correspond to symmetrical partial wheel brake loss failure scenarios with active alarm notification and without active alarm notification respectively. The independent top-level types HydraulicLossBlue, HydraulicLossGreen, and HydraulicLossComponents correspond to pressure loss failures of the blue hydraulic circuit, green hydraulic circuit, and generic hydraulic components respectively. The independent top-level types SoftwareFailure and HardwareFailure correspond to generic software failure and generic hardware failure scenarios respectively, with no inheritance relationship to the AnyImplementationError base type. Two error set types shall be defined for batch failure scenario matching. The first set type is WBErrorSet, with fixed members including TotalWBLossAnunciated, TotalWBLossUnanunciated, PartialSymmetricalWBLoss, AssymetricalWBLoss, and InadvertentWB, covering all core wheel brake function failure scenarios. The second set type is HydraulicErrors, with fixed members including HydraulicLossBlue, HydraulicLossGreen, HydraulicLossComponents, and NoService, covering all failure scenarios related to the hydraulic pressure supply chain. Two reusable two-state error behavior state machine templates shall be defined in the package. The first template is named Twostate, which shall reference error type definitions from WBSFunctionalErrorLib, and configure two mutually exclusive states. The Operational state is set as the initial state, representing that the bound component is in a normal available operational state, while the failed state is a general failure state representing that the bound component is in an invalid unavailable state. The failure state of this state machine is not bound to a specific error type set, and can be reused as a basic two-state failure model for general system components. The second template is named TwostateWBS, which shall reference error type definitions from WBSFunctionalErrorLib, and configure two mutually exclusive states. The Operational state is set as the initial state, representing that bound wheel brake components are in a normal available operational state, while the Failed state is a hydraulic-related failure state. This Failed state shall be associated with the HydraulicErrors error set, meaning the state shall transition to the Failed state when the bound component triggers any error contained in the HydraulicErrors set. This state machine is dedicated for binding to components associated with the wheel brake hydraulic supply chain.
