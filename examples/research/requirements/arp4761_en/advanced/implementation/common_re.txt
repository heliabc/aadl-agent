The system shall define a standalone public shared package with the fully qualified identifier impl::common. All elements declared within this package shall be configured with public access permissions to support unobstructed cross-module reference by upper-layer functional components across the system. This package shall not declare dependencies on any other external packages, and shall function as the centralized storage location for universally reusable bus definitions and data type definitions required for full system modeling.

This common package shall only define foundational interaction carriers and data classification entities, and shall not contain executable functional component definitions including processes, threads, devices, subsystems, or abstract components. No dedicated external interaction ports, internal subcomponent slots, or pre-defined connection interfaces shall be specified within this package. All bus and data type entities defined in this package shall serve as standardized foundational interface elements that upper-layer functional components may instantiate and reference when constructing their own external service interfaces and internal interconnection interfaces.

This common package shall not define fixed end-to-end data flow paths, as it does not bind to specific functional execution nodes, hardware endpoints, or logical connection links. The transmission direction, source endpoints, destination endpoints, and data mapping rules for information carried by instances of the buses and data types defined in this package shall be explicitly specified by upper-layer business components during component implementation, subsystem integration, and system deployment stages.

This common package shall not attach fixed scheduling policies, periodic execution triggers, transmission latency budgets, response time requirements, or hard deadline constraints to the defined buses and data types, as these definitions are designed for universal reuse across diverse application scenarios. All timing, scheduling, and latency related constraints associated with deployed instances of these buses and data types shall be configured by upper-layer application components in alignment with specific business scenario performance requirements during system integration and deployment.

For communication bus definition rules, the system shall define a power bus type named power, paired with a generic implementation named power.generic. This bus type shall be used to carry electrical power supply transmission between connected system components, and the generic implementation shall be directly applicable to all general power supply scenarios that do not require customized transmission protocols or special signal characteristics. The system shall define a pulse width modulation bus type named pwm, paired with a generic implementation named pwm.generic. This bus type shall be used to carry pulse width modulation signal transmission between connected components, and the generic implementation shall be directly applicable to all general PWM signal interaction scenarios that do not require customized encoding rules or special timing configurations. The system shall define a pressure signal bus type named pressure, paired with a dedicated implementation named pressure.i. This bus type shall be used to carry pressure measurement and control signal transmission between field sensing devices, pump actuators, and other pressure-related components, and shall act as the mandatory standard carrier for all pressure-related interaction across the system. For data type definition rules, the system shall define a base control command data type named command, which serves as the parent type for all control command class data transmitted across the system. Four concrete, scenario-specific implementations shall be defined under the base command data type. The command.brake implementation shall be used to encapsulate and carry braking-related control instructions for vehicle deceleration and stopping functions. The command.skid implementation shall be used to encapsulate and carry control instructions for skid condition detection, response, and vehicle stability regulation functions. The command.pedal implementation shall be used to encapsulate and carry control instructions generated in response to driver accelerator or brake pedal operation inputs. The command.announce implementation shall be used to encapsulate and carry control instructions for in-vehicle audio announcement, status prompt, and human-machine interaction notification functions.
