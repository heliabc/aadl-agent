The top-level public package is named impl::bscu, which declares explicit import dependencies on the common package, platform package, Base_Types package, EMV2 annex library, and ARP4761 annex library to access shared data types, bus definitions, platform component models, error modeling constructs, and safety assessment property sets respectively. The package is structured in a hierarchical component composition model, containing two process component types with associated implementations, three system component types with a total of five associated implementations, including two extended implementation variants for different deployment platforms. Component dependency relationships follow a strict top-down hierarchy: the top-level brake system control unit (BSCU) system depends on instances of the BSCU subsystem component and the alternate selection logic component for redundant operation, each BSCU subsystem depends on instances of the command process and monitor process to execute core control and monitoring functions, and the federated and integrated modular avionics (IMA) deployment variants of the BSCU depend on corresponding platform components from the imported platform package to support processor resource binding. No circular dependencies are permitted across component boundaries.

All component functional interfaces are defined at the component type level, with implementation-specific extensions limited to internal subcomponents, connections, error behavior, and deployment properties. The command process type exposes three external data ports: one input data port named pedalvalue typed to common::command.pedal for incoming pedal position data, two output data ports named brake and skid typed to common::command.brake and common::command.skid respectively for generated brake and skid command outputs. The command.i process implementation adds no external functional features, and defines internal error propagation points including an implicit processor-facing input propagation point carrying SoftwareFailure and HardwareFailure error types, an incoming NoService error propagation on the pedalvalue port, and outgoing NoValue error propagation on the brake and skid ports. The monitor process type exposes three external data ports: two input data ports named brake and skid typed to common::command.brake and common::command.skid respectively for incoming command data to validate, one output data port named valid typed to Base_Types::Boolean for validity status output. The monitor.i process implementation adds no external functional features, and defines internal error propagation points including an implicit processor-facing input propagation point carrying SoftwareFailure and HardwareFailure error types, incoming NoValue error propagation on the brake and skid ports, outgoing NoValue error propagation on the valid port, plus an internal InvalidReport error event representing spontaneous incorrect validity reporting. The bscu_subsystem system type exposes five external interfaces: one required bus access port named pwr for connection to the common::power.generic power bus, one input data port named pedal typed to common::command.pedal for incoming pedal position data, two output data ports named cmd_brk and cmd_skid typed to common::command.brake and common::command.skid respectively for processed command outputs, one output data port named valid typed to Base_Types::Boolean for subsystem validity status. The bscu_subsystem.generic implementation encapsulates two internal subcomponents: one instance of monitor.i named mon, one instance of command.i named cmd, with internal port connections routing external pedal input to the command process, routing command process brake and skid outputs to the monitor process for validation, routing command process brake and skid outputs to the external cmd_brk and cmd_skid ports respectively, and routing monitor process validity output to the external valid port. The select_alternate system type exposes three external data ports: two input data ports named input1 and input2 typed to Base_Types::Boolean for incoming subsystem validity signals, one output data port named result typed to Base_Types::Boolean for alternate selection control output. The select_alternate component defines internal error propagation points including incoming NoValue error propagation on both input ports, outgoing NoValue error propagation on the result port, plus an internal InternalError event representing spontaneous incorrect selection behavior. The top-level bscu system type exposes seven external interfaces: two required bus access ports named pwr1 and pwr2 for connection to independent common::power.generic power buses, two input data ports named pedal1 and pedal2 typed to common::command.pedal for independent pedal position inputs to each redundant channel, one output data port named Select_Alternate typed to Base_Types::Boolean for subsystem selection control output, two output data ports named cmd_nor and cmd_alt typed to common::command.skid for normal and alternate mode skid command outputs respectively. The bscu.basic implementation provides a non-redundant configuration with no internal subcomponents, and adds incoming NoPower error propagation on both power access ports. The bscu.generic implementation encapsulates three internal subcomponents: two instances of bscu_subsystem.generic named sub1 (primary channel) and sub2 (alternate channel), one instance of select_alternate named select, with internal connections routing external power and pedal inputs to the corresponding BSCU subsystem, routing subsystem validity outputs to the select component inputs, routing select component output to the external Select_Alternate port, and routing subsystem skid command outputs to the corresponding external cmd_nor and cmd_alt ports; the subsystem brake command ports have no connection to top-level BSCU ports in this implementation. The bscu.federated implementation extends bscu.generic without modifying external interfaces, adding one internal subcomponent instance of platform::platform.federated named platform to represent federated avionics hardware. The bscu.ima implementation extends bscu.generic without modifying external interfaces, adding one internal subcomponent instance of platform::platform.ima named platform to represent integrated modular avionics hardware.

Nominal data flow through the system follows fixed, unidirectional paths from input interfaces to output interfaces, with no cyclic data paths. Power is supplied via independent external connections to pwr1 and pwr2, with power from pwr1 delivered exclusively to the primary BSCU subsystem sub1, and power from pwr2 delivered exclusively to the alternate BSCU subsystem sub2 to maintain power supply isolation between redundant channels. Pedal position data received on the pedal1 input is routed directly to the pedal input of sub1, while pedal position data received on the pedal2 input is routed directly to the pedal input of sub2 to maintain input signal isolation between redundant channels. Within each BSCU subsystem, incoming pedal data is passed to the pedalvalue input of the internal command process, which processes raw pedal position values to generate calibrated brake and skid command data. The brake and skid command data from the command process is split along two parallel paths: one path delivers the command data to the corresponding inputs of the internal monitor process for validity checking, while the other path delivers the brake command data to the subsystem cmd_brk port and skid command data to the subsystem cmd_skid port. The monitor process evaluates received brake and skid command data to confirm data integrity and validity, producing a Boolean validity signal that is routed to the external valid port of the BSCU subsystem. The validity signal from the primary subsystem sub1 is routed to the input1 port of the select_alternate component, while the validity signal from the alternate subsystem sub2 is routed to the input2 port of the select_alternate component. The select_alternate component executes fixed selection logic based exclusively on the primary subsystem validity signal received on input1: if the primary subsystem validity signal indicates valid operation (true value), the component outputs a false value on the result port to select the primary subsystem for active operation; if the primary subsystem validity signal indicates invalid operation (false value), the component outputs a true value on the result port to select the alternate subsystem for active operation. The validity signal from the alternate subsystem received on input2 is used solely for error detection purposes, with no impact on nominal selection logic. The result output of the select_alternate component is routed directly to the external Select_Alternate port of the top-level BSCU to communicate active channel status to downstream components. Skid command data from the primary subsystem sub1 is routed to the external cmd_nor output for delivery during normal primary operation, while skid command data from the alternate subsystem sub2 is routed to the external cmd_alt output for delivery during alternate backup operation. Error propagation flows follow defined paths aligned with nominal data connections: loss of pedal input service propagates into the command process, which transforms the NoService error to a NoValue error on outgoing brake and skid command ports; NoValue errors on command data ports propagate into the monitor process, which triggers a NoValue error on the outgoing validity port; loss of power to a BSCU subsystem propagates to trigger a NoValue error on the subsystem validity port; NoValue errors on both select_alternate inputs, or internal select component errors, trigger a NoValue error on the select result output. Composite error state logic for each BSCU subsystem defines a failed state if either the internal command or monitor process is in a failed state, and an operational state only if both processes are operational. Composite error state logic for the redundant bscu.generic, bscu.federated, and bscu.ima implementations defines a total failed state only if both BSCU subsystems are failed, an alternate operational state if the primary subsystem is failed and the alternate is operational, or if both subsystems are operational but the select component is failed, and a fully operational state only if both subsystems and the select component are operational.

Scheduling and resource allocation rules are defined via explicit processor binding properties for each deployment variant, with no implicit resource sharing permitted across bound execution contexts. For the bscu.federated deployment variant, the command and monitor processes of the primary subsystem sub1 are bound exclusively to the cpu1 processor of the federated platform, while the command and monitor processes of the alternate subsystem sub2 are bound exclusively to the cpu2 processor of the federated platform, establishing independent scheduling domains for each redundant channel on separate physical processors to eliminate cross-channel compute interference. For the bscu.ima deployment variant, the primary subsystem command process is bound exclusively to partition1 of the IMA platform CPU, the primary subsystem monitor process is bound exclusively to partition2 of the IMA platform CPU, the alternate subsystem command process is bound exclusively to partition3 of the IMA platform CPU, and the alternate subsystem monitor process is bound exclusively to partition4 of the IMA platform CPU, enforcing strict time and space partitioning between all four process instances per IMA scheduling rules to prevent cross-partition fault propagation. Error state transitions are event-driven, triggering immediately upon detection of a qualifying error condition without intentional delay: the command process transitions from operational to failed state immediately upon detection of a NoService error on the pedal input, or a SoftwareFailure or HardwareFailure from the hosting processor; the monitor process transitions from operational to failed state immediately upon detection of a NoValue error on brake or skid inputs, a SoftwareFailure or HardwareFailure from the hosting processor, or an internal InvalidReport event; each BSCU subsystem transitions from operational to failed state immediately upon detection of a NoPower error on the power input; the select_alternate component transitions from operational to failed state immediately upon detection of NoValue errors on both input ports simultaneously, or an internal InternalError event that causes an uncommanded switch to alternate mode; the non-redundant bscu.basic implementation transitions from operational to failed state immediately upon detection of a NoPower error on either individual power input, while the redundant bscu.generic, bscu.federated, and bscu.ima implementations transition to total failed state only upon detection of NoPower errors on both independent power inputs. Safety-related occurrence and classification constraints are defined per ARP4761 requirements: the InvalidReport event in the monitor process is classified as a Minor hazard with a Probable qualitative probability objective, representing an erroneous monitor report that could trigger an invalid switch to alternate mode; failure of a single BSCU subsystem is classified as a Major hazard with a Probable qualitative probability objective, with a fixed occurrence rate of 3.3e-5 per operational hour, with critical consequence only if both redundant subsystems fail simultaneously; the InternalError event in the select_alternate component is classified as a Hazardous hazard with an ExtremelyImprobable qualitative probability objective, with a Poisson distributed occurrence rate of 3.6e-6 per operational hour; loss of a single power supply line is classified as a Hazardous hazard with a Remote qualitative probability objective, with critical consequence only if both independent power supplies are lost.

All communication buses and data types used across the system are sourced from imported shared packages to ensure consistent type definition across the full system model. The only bus type used for power delivery is common::power.generic, which is accessed via required bus access ports on each BSCU subsystem, supporting unidirectional power delivery from external power sources to subsystem components, with a defined NoPower error state representing complete loss of bus supply. All data port communications use sampled, most-recent-value data transfer semantics with no event queuing, consistent with standard AADL data port behavior for periodic or sampled control systems. Data type assignments for all ports are fixed and cannot be modified without updating the shared type definitions: pedal position input ports use the common::command.pedal data type to represent raw pedal position measurements, brake command ports use the common::command.brake data type to represent calibrated brake command values, skid command ports use the common::command.skid data type to represent calibrated skid correction command values, all validity status ports and selection control ports use the Base_Types::Boolean data type to represent binary true/false state values. Error types associated with communication interfaces are sourced from the WBSImplementationErrorLib error library, with fixed propagation rules: pedal input ports carry the NoService error type to indicate absence of valid pedal input data, command and validity output ports carry the NoValue error type to indicate absence of valid output data, processor binding points carry SoftwareFailure and HardwareFailure error types to indicate compute platform faults, power bus access points carry the NoPower error type to indicate loss of electrical supply. All safety property assignments adhere to ARP4761 standard definitions for hazard classification, probability objectives, and cross-referencing to system safety assessment artifacts.
