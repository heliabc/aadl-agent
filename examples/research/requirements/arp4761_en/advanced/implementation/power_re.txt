The system shall define a public AADL package identified as impl::power. This package shall import three required external packages to access pre-defined shared constructs: the common package containing generic cross-package resource specifications, the ARP4761 package containing standardized aviation safety and hazard assessment property definitions, and the EMV2 package containing error modeling language constructs and associated reliability properties. The package shall declare two top-level component types, each paired with a single concrete implementation definition. The first component is categorized as a hardware device, named battery, with a corresponding implementation named battery.generic that contains no internal subcomponents or internal connections. The second component is categorized as a system, named power, with a corresponding implementation named power.generic. The power.generic implementation shall instantiate two identical device subcomponents of type battery.generic, labeled battery1 and battery2, which operate as independent redundant power supply units with no additional nested subcomponents.

The battery device type shall expose one core functional feature: a provided bus access port named socket, typed to match the common::power.generic bus defined in the imported common package. The battery device shall implement EMV2 error modeling constructs that import error type definitions from WBSImplementationErrorLib and reference the Twostate error behavior specification from WBSImplementationErrorLib. The battery device shall define formal error propagation interfaces, including an outbound propagation path for NoPower errors transmitted via the socket port, and an outbound propagation path for AnyImplementationError transmitted via component binding paths. The battery device shall define two root error flow sources: error flow f1 that sources NoPower errors at the socket port, and error flow f2 that sources AnyImplementationError at the component binding layer. The battery device shall define two internal error events: the Depleted event indicating complete discharge of stored electrical energy, and the Explode event indicating catastrophic structural failure of the battery unit. The battery device shall implement a two-state error behavior state machine with two mutually exclusive states: the Operational state representing normal, fully functional operation, and the Failed state representing total loss of intended power supply function. Defined state transitions for the battery shall include a transition from Operational to Failed triggered by occurrence of the Depleted event, and a transition from Operational to Failed triggered by occurrence of the Explode event. Formal error propagation rules for the battery shall specify that the Failed state propagates the NoPower error via the socket port with no conditional guard, and the Operational state propagates the NoError status via the socket port with no conditional guard. Safety and reliability properties for the battery shall be assigned in compliance with ARP4761 and EMV2 requirements. The NoPower error propagated from the socket port shall carry ARP4761 hazard attributes including a cross-reference to ARP4761 page 277 figure 9, a failure mode description of single power source loss that presents critical risk if both primary and redundant power sources are lost, applicability to Landing and RTO flight phases, a hazard description of total electrical power loss to the BSCU, a FailureConditionClassification value of Major, a QualitativeProbabilityObjective value of Probable, and supporting notation that the condition becomes a major hazard when both power sources are lost. The NoPower error at the socket port shall have an EMV2 OccurrenceDistribution property specifying a Poisson distribution with a probability value of 1.35e-5. The Explode error event shall carry ARP4761 hazard attributes including a TBD cross-reference, a failure mode description of battery explosion, applicability to all flight phases, a hazard description of battery explosion as a high-severity hazard, a FailureConditionClassification value of Catastrophic, a QualitativeProbabilityObjective value of ExtremelyImprobable, and supporting notation that the failure causes physical impact to adjacent surrounding components. The Depleted error event shall carry ARP4761 hazard attributes including a TBD cross-reference, a failure mode description of battery charge depletion, applicability to all flight phases, a hazard description of total loss of stored battery energy, a FailureConditionClassification value of Major, a QualitativeProbabilityObjective value of Probable, and supporting notation that the condition presents operational risk if the redundant battery unit also experiences failure. The power system type shall expose two core functional features: two provided bus access ports named line1 and line2, both typed to match the common::power.generic bus defined in the imported common package. The power system shall implement EMV2 error modeling constructs that import error type definitions from WBSImplementationErrorLib and reference the Twostate error behavior specification from WBSImplementationErrorLib. The power system shall define a formal error propagation interface for outbound propagation of AnyImplementationError transmitted via system binding paths, with one root error flow source f0 that sources AnyImplementationError at the system binding layer. The power.generic system implementation shall define two bidirectional bus access connections: connection pwr1 shall link the socket port of subcomponent battery1 to the external system port line1, and connection pwr2 shall link the socket port of subcomponent battery2 to the external system port line2, with no additional internal port connections defined.

Functional power flow within the power.generic implementation shall follow fully isolated, non-interacting redundant paths. Subcomponent battery1 shall supply electrical power exclusively through its socket port, routed via connection pwr1 to the external line1 port for access by connected external consuming systems. Subcomponent battery2 shall supply electrical power exclusively through its socket port, routed via connection pwr2 to the external line2 port for access by connected external consuming systems. No cross-connection, load sharing, or power switching logic shall exist between the two power paths, ensuring fully independent operation of the two supply channels. Error flow within the system shall follow direct, unfiltered propagation paths. Errors generated by internal battery error events shall trigger the defined state transitions in the battery error behavior model, with resulting port-level errors passed directly along the dedicated bus connections to the corresponding external system ports. No system-level error filtering, conversion, masking, or redundancy management logic shall be applied to errors propagated from the battery subcomponents. Implementation errors originating at the binding layers of battery1, battery2, or the top-level power system shall propagate outward via their respective binding paths without modification or aggregation.

All components defined within the impl::power package represent statically deployed hardware elements for electrical power delivery, with no software execution entities such as threads, processes, or scheduled subprograms included in the package structure. No periodic scheduling, priority-based preemption, or time-partitioned execution rules shall apply to these components. All error event detection and associated state transitions shall occur as immediate, event-triggered responses with no mandated execution latency budget. Error propagation along bus connections and binding paths shall occur instantaneously, with no defined minimum or maximum transmission delay requirements for power delivery or error signaling.

The impl::power package shall not define custom abstract data types or custom bus types. All power transmission across component boundaries shall use the imported common::power.generic bus as the sole communication medium. All bus access connections shall support bidirectional access semantics to align with the provided bus access port configuration. The common::power.generic bus shall carry continuous electrical power as its primary service payload, with no defined discrete application data exchange, message framing, or higher-level protocol requirements for communication across the bus.
