The modeled platform domain is encapsulated within the impl::platform package, which explicitly imports the EMV2 error modeling annex library and ARP4761 safety assessment property library as mandatory external dependencies. All error behavior definitions within the package rely on types and behavior constructs from the external WBSImplementationErrorLib error library, specifically its Twostate dual-state error behavior state machine and associated error type set. The package defines a hierarchical component structure starting with the virtual processor type partition and its generic, feature-free implementation partition.generic, the processor type cpu and its two architecture-specific implementations, namely cpu.ima for integrated modular avionics deployments and cpu.single for federated architecture deployments, as well as the abstract top-level system type platform and its two corresponding concrete implementations, namely platform.ima for IMA platform configurations and platform.federated for federated platform configurations. No additional component types, implementations, or library elements are defined within the package scope.

For component external interfaces and internal structural specifications, the virtual processor partition type defines two error propagation ports: an outbound propagation port named bindings that supports transmission of SoftwareFailure and HardwareFailure error types, and an inbound propagation port named processor that supports reception of HardwareFailure error types. Internally, the partition component declares a SoftwareFailure error event, initializes to the Operational state upon activation, and triggers a state transition to the Failed state when the SoftwareFailure event occurs. When operating in the Operational state, the component propagates a NoError status through the outbound bindings port; when operating in the Failed state, the component propagates a SoftwareFailure error through the same bindings port. The partition.generic implementation is a general-purpose realization of the partition type that adds no supplementary subcomponents, ports, properties, or behavior logic beyond the definitions inherited from the base partition type. The processor cpu type defines a single outbound error propagation port named bindings that supports transmission of HardwareFailure error types. Internally, the cpu component declares an InternalFailure error event, initializes to the Operational state upon activation, and triggers a state transition to the Failed state when the InternalFailure event occurs. When operating in the Operational state, the component propagates a NoError status through the outbound bindings port; when operating in the Failed state, the component propagates a HardwareFailure error through the same bindings port. The cpu.ima implementation, built to support IMA architecture configurations, contains four identical virtual processor subcomponents named partition1, partition2, partition3, and partition4, each instantiating the partition.generic implementation. This processor implementation does not define independent software failure propagation logic at the processor hardware level, as all software-related failure behavior is encapsulated within the nested partition subcomponents. The cpu.single implementation, built to support federated architecture configurations, inherits the base cpu type’s bindings port for hardware failure propagation, and adds an additional outbound error propagation port named processor that supports transmission of SoftwareFailure error types. Internally, this implementation declares a dedicated SoftwareFailure error event, propagates a NoError status through the processor port when in the Operational state, triggers a state transition from Operational to Failed when the SoftwareFailure event occurs, and propagates a SoftwareFailure error through the processor port when in the Failed state. This implementation contains no nested virtual processor partition subcomponents. The top-level platform system type acts as an abstract root for platform configurations, with no predefined external ports or internal subcomponents at the type level. The platform.ima implementation, representing a complete IMA platform, contains a single processor subcomponent named cpu that instantiates the cpu.ima processor implementation. The platform.federated implementation, representing a complete federated platform, contains two processor subcomponents named cpu1 and cpu2, both of which instantiate the cpu.single processor implementation.

For system propagation flow paths, the partition component defines two dedicated error flows. The first flow, named fsoft, acts as an error source that routes internally triggered SoftwareFailure events directly outward through the bindings port. The second flow, named fhard, acts as a pass-through error path that routes HardwareFailure errors received on the inbound processor port directly outward through the bindings port, with no internal error transformation, filtering, or aggregation applied. The base cpu component defines a single error source flow named f1 that routes HardwareFailure errors caused by internal InternalFailure events directly outward through the bindings port. The cpu.single implementation defines an additional error source flow named fsoft that routes internally triggered SoftwareFailure events directly outward through the dedicated processor error propagation port. All defined error flows follow unidirectional propagation rules aligned with port directionality.

For timing, scheduling, and associated constraint specifications, all platform components use an event-triggered execution model for both operational state management and error state transitions, with no defined periodic scheduling policies, task worst-case execution time budgets, or end-to-end communication latency requirements specified for platform elements. All declared error events adhere to defined occurrence probability distributions: the SoftwareFailure event on partition components follows a Poisson distribution with a probability value of 1.35e-5, the InternalFailure event on base cpu components follows a Poisson distribution with a probability value of 1.35e-5, and the SoftwareFailure event on cpu.single implementations follows a Poisson distribution with a probability value of 1.35e-5. In compliance with ARP4761 safety assessment requirements, each of the three defined error events is assigned a Major failure condition classification, a Probable qualitative probability objective, and applicability across all system operational phases. The SoftwareFailure event on partition components corresponds to platform software faults such as operating system exceptions, with an impact scope covering all software components managed by the affected partition. The InternalFailure event on cpu components corresponds to hardware faults affecting processors or attached peripheral devices, with an impact scope covering all software components bound to the affected hardware resource. The SoftwareFailure event on cpu.single implementations corresponds to platform software faults such as operating system exceptions, with an impact scope covering all software components controlled by the affected processor. All hazard entries carry a to-be-determined cross-reference identifier, an empty formal failure identifier field, and descriptive comment text documenting impact scope at the initial modeling stage.

For data type and communication bus definition rules, no custom application-level data types are declared within the package. All values transmitted across component error propagation ports are typed as error constructs imported from the external WBSImplementationErrorLib library, consisting of three discrete valid values: NoError, SoftwareFailure, and HardwareFailure. No dedicated communication bus components, bus protocol specifications, or bus access policy definitions are included within the package, as all modeled interactions are limited to error propagation between hierarchically nested platform components, with no explicit modeling of general-purpose communication fabric for application data exchange.
