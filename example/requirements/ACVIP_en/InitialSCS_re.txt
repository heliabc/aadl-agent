All system modeling elements shall be encapsulated within the public InitialSCS package, which serves as the top-level namespace for all component definitions, data type declarations, and implementation artifacts. The top-level system type is defined as HighLevelSCS, with a corresponding implementation HighLevelSCS.i that acts as the system integration layer. The HighLevelSCS.i implementation shall contain three subcomponents with strict hierarchical containment: the first subcomponent is sensor1, typed as the SimpleSensor device and instantiated from the SimpleSensor.i device implementation; the second subcomponent is controller1, typed as the SimpleController system and instantiated from the SimpleController.i system implementation; the third subcomponent is brake1, typed as the SimpleBrake device and instantiated from the SimpleBrake.i device implementation. Dependency relationships between elements shall be explicitly bounded: the HighLevelSCS.i implementation depends on the type and implementation definitions of all three contained subcomponents, no subcomponent shall contain nested child components, interaction dependencies between subcomponents are established exclusively through port connections declared at the top-level system implementation, and all component port definitions depend on package-scoped data type declarations to enforce port type consistency.

Each component shall define explicit external feature interfaces and internal flow anchors without hidden interaction points. The SimpleSensor device type shall expose a single external feature: dataOut, an outgoing data port that serves as the component’s only outbound data interface. SimpleSensor shall define an internal flow source named sensorFlow anchored to the dataOut port, marking the origination point of associated data flows. The SimpleSensor.i device implementation shall not add or modify external features, and shall only contain configuration properties applied to its internal flow. The SimpleController system type shall expose two external data port features: dataIn, an incoming data port for receiving upstream sensor data, and dataOut, an outgoing data port for sending downstream control signals. SimpleController shall define an internal flow path named controllerFlow that traces the data transit path from the dataIn input port to the dataOut output port, representing the internal data processing passage of the controller. The SimpleController.i system implementation shall not add or modify external features, and shall only contain configuration properties applied to its internal flow path. The SimpleBrake device type shall expose a single external feature: dataIn, an incoming data port that serves as the component’s only inbound data interface for receiving control signals. SimpleBrake shall define an internal flow sink named brakeFlow anchored to the dataIn port, marking the termination point of associated data flows. The SimpleBrake.i device implementation shall not add or modify external features, and shall only contain configuration properties applied to its internal flow sink. The HighLevelSCS top-level system type shall not expose any external interaction ports, and its HighLevelSCS.i implementation shall not add top-level external ports, only handling internal subcomponent interconnection.

All data transmission within the system shall follow a unidirectional serial topology with no branches, feedback loops, or parallel forwarding paths. Two explicit port connections shall be declared in the HighLevelSCS.i implementation to bind subcomponent ports. The first connection, identified as c1, shall connect the dataOut output port of the sensor1 subcomponent to the dataIn input port of the controller1 subcomponent, enabling unidirectional transfer of sensor sampling data from the sensor to the controller. The second connection, identified as c2, shall connect the dataOut output port of the controller1 subcomponent to the dataIn input port of the brake1 subcomponent, enabling unidirectional transfer of brake control signals from the controller to the brake actuator. An end-to-end flow identified as ete1 shall be defined across the full signal chain, tracing the complete data path starting from the sensorFlow flow source inside sensor1, traversing connection c1 to reach controller1, passing through the controllerFlow internal flow path inside controller1, traversing connection c2 to reach brake1, and terminating at the brakeFlow flow sink inside brake1.

Latency constraints shall be applied exclusively to individual internal flow segments of each component, with no additional global scheduling rules or connection-specific latency assignments defined. For the SimpleSensor.i implementation, a latency bound of 3 milliseconds to 5 milliseconds shall be applied to the sensorFlow flow source, covering the full processing duration from physical signal sampling to valid data availability on the dataOut port. For the SimpleController.i implementation, a latency bound of 3 milliseconds to 5 milliseconds shall be applied to the controllerFlow flow path, covering the full processing duration from valid data reception on the dataIn port to control computation completion and valid signal availability on the dataOut port. For the SimpleBrake.i implementation, a latency bound of 3 milliseconds to 5 milliseconds shall be applied to the brakeFlow flow sink, covering the full processing duration from valid signal reception on the dataIn port to completion of the brake actuation action. The aggregate end-to-end latency for the ete1 flow shall be the cumulative sum of the latency bounds of all traversed flow segments, as no additional latency is introduced by the direct port connections between components. No periodic dispatch schedules, execution time budgets, or priority assignments shall be specified for any component in the system.

Two package-scoped data types shall be defined to standardize data payloads across all port interfaces, with no nested data structure declarations for either type. The first data type is SensorData, which acts as the standardized type for sensor sampling output, and shall be used to type the dataOut port of SimpleSensor and the dataIn port of SimpleController to ensure type matching across connected ports. The second data type is BrakeSignal, which acts as the standardized type for brake control output signals, and shall be used to type the dataOut port of SimpleController and the dataIn port of SimpleBrake to ensure type matching across connected ports. All port connections shall only be established between ports with identical assigned data types, and cross-type port connections are prohibited. No dedicated bus components, virtual bus components, or bus access features shall be defined within the package. All inter-component communication shall occur via direct point-to-point data port connections without intermediate bus forwarding, protocol encapsulation, bus arbitration, or bandwidth allocation mechanisms.
