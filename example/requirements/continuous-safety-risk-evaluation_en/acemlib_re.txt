A public top-level AADL package named acemlib shall be defined to serve as a shared, reusable model library supporting adaptive cruise control and flight control system error modeling for aviation applications. The acemlib package shall operate as an independent library unit with no declared dependencies on external AADL packages, and shall mark all contained model elements as publicly accessible to support reference from downstream system, software, and platform models. The acemlib package shall not include nested sub-packages, and shall embed an EMV2 error modeling annex as its sole core content, with no native component implementations, connection logic, or platform definitions contained directly within the package scope.

The acemlib package shall not define any concrete component types or component implementations, including but not limited to system, process, thread, thread group, device, memory, processor, or abstract component definitions. As no executable or structural components are defined within the package, no external component interfaces, internal subcomponent interfaces, feature definitions, port declarations, access points, or feature group specifications shall be included in the package. All constructs contained in the package are static, reusable error modeling artifacts designed to be referenced and applied to components defined in separate model packages, rather than representing runtime functional components with interface requirements.

The acemlib package shall not define concrete runtime system data flow paths, data transfer connections, data transformation logic, or data routing rules, as no functional components or connection bindings are specified within the package. The error types and error behavior state machines contained in the package act as annotation metadata to support failure propagation analysis and error state tracking for data flows defined in dependent system models, and do not themselves specify functional data movement between system elements. No end-to-end flow specifications, flow implementations, or flow-related latency properties shall be declared within the acemlib package.

The acemlib package shall not define any schedulable execution elements, and thus shall not specify thread dispatch protocols, scheduling policies, processor allocation rules, execution time budgets, worst-case execution time constraints, end-to-end latency requirements, deadline values, period values, or clock synchronization rules. The error state machines defined in the package’s EMV2 annex shall not include hard timing constraints for state transition triggers, state dwell times, or error propagation delays, as such timing attributes are intended to be specified in the individual component models that apply the library’s error modeling constructs. No scheduling-related properties shall be attached to elements within the acemlib package.

For data type definition rules, the acemlib package shall not declare native AADL data component types or data implementations used for runtime data exchange between components. All typed constructs within the package are EMV2-native error types defined exclusively for error modeling purposes, which shall include the Incident base error type, the ACCFail error type representing adaptive cruise control functional failure, the PilotFlightControlMistake error type representing erroneous pilot flight control input, the ACCFailUnawareFlightControlMistake error type representing pilot control errors induced by lack of awareness of an active ACC failure, the AOADiscrepancyUnawarePilotMistake error type representing pilot control errors induced by lack of awareness of angle of attack measurement discrepancies, the NoPilotControl error type representing total loss of valid pilot control input, the NoACCTurnOff error type representing failure to disable the ACC system when operationally required, the NoACCKnowledgeNoTurnoff error type representing ACC disable failure caused by pilot unawareness of active ACC status, the AOADiscrepancyUnawareNoTurnoff error type representing ACC disable failure occurring when the pilot is unaware of angle of attack discrepancies, the AOADiscrepancyAwareNoTurnoff error type representing ACC disable failure occurring even when the pilot has awareness of angle of attack discrepancies, the BadACCControl error type representing transient incorrect ACC control command output, and the ContinuousBadACCControl error type representing sustained, repeated incorrect ACC control command output across consecutive control cycles. The EMV2 annex within the package shall define two reusable error behavior state machines. The first state machine, named ACCStates, shall model the operational and fault states of ACC components, with the operational state set as the initial state representing fully functional normal ACC operation, and four additional non-initial states including badcontrol for transient incorrect control output, continuousbadcontrol for persistent incorrect control output, standby for non-active ACC standby mode, and failed for permanent ACC functional loss. The second state machine, named ClimbControlStates, shall model climb control authority handover between the ACC system and pilot, with the ACCInCharge state set as the initial state representing ACC-held primary climb control authority, and one additional non-initial state named PilotInCharge representing pilot-held primary climb control authority. For communication bus definition rules, the acemlib package shall not define any bus types, bus implementations, virtual bus types, virtual bus implementations, bus access protocols, or bus-related property constraints, as the package is scoped exclusively to error model library content rather than platform communication architecture definitions. No bus access features or bus connection bindings shall be specified within the package.
