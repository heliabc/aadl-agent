The entire system is encapsulated within the public package AircraftSafetyExample::AOADiscrepancy, which holds all component type definitions, component implementations, and associated error model specifications. All components with embedded error behavior depend on two external error model libraries, ErrorLibrary and acemlib, to provide standard error type definitions and error state machine behavior specifications. The package defines six top-level component types: the aoasensor device component representing the angle-of-attack measurement sensor, the AuxClimbControl abstract component representing the auxiliary climb control function, the pilot abstract component representing pilot operational behavior, the flightsurface device component representing the aircraft flight control surface actuation hardware, the aoadiscrepancydetector device component representing the angle-of-attack reading discrepancy monitoring unit, and the Engine device component representing the aircraft propulsion engine. The package also defines the ac system component as the top-level aircraft system assembly. Component implementation hierarchy follows a strict extension and refinement structure. The AuxClimbControl component has one concrete implementation named sensor1, which realizes single-sensor input control logic. The pilot component has a base nominal implementation representing nominal pilot operation, and one extended implementation named NoACCKnowledge that inherits all features and logic from the nominal implementation while adding error behavior for pilots without relevant ACC operation knowledge. The aoadiscrepancydetector component has a base standard implementation, and one extended implementation named permanentFail that realizes permanent failure behavior of the detector. The ac system component has a base common implementation that defines core system composition and connections, with three sequentially extended implementations: the OneSensorSpec implementation that adds discrepancy monitoring hardware to the common base, the OSSPermanentDiscrepancyFail implementation that refines the discrepancy detector instance in OneSensorSpec to the permanent failure version, and the OSSNoACCKNowledge implementation that further refines the pilot instance in OSSPermanentDiscrepancyFail to the NoACCKnowledge version. No circular dependencies exist across component definitions or implementations, with all extended versions retaining full compatibility with the interface contracts of their parent implementations.

Each component defines explicit external interface features and internal behavior rules aligned with functional and fault propagation requirements. The aoasensor device exposes a single out data port named aoareading for transmitting measured angle-of-attack readings. This port propagates two outbound error types: BadValue representing incorrect sensor measurement output, and ServiceOmission representing missing sensor output. The sensor defines an error flow source named reading tied to the aoareading port, with an occurrence probability of 1.0E-5 for BadValue errors and 1.1E-5 for ServiceOmission errors. The AuxClimbControl abstract component exposes five external features: two in data ports named aoa1 and aoa2 for receiving angle-of-attack readings from two separate sensors, one in feature port named ACCOnOff for receiving ACC on/off control commands, one out feature port named controlsurfacecmd for transmitting control commands to the flight surface, and one out feature port named ACCStandbyIndicator for transmitting ACC standby status signals. The component accepts two inbound error types on its input ports: BadValue and ServiceOmission on the aoa1 port, and NoACCTurnOff representing failure to send an ACC shutdown command on the ACCOnOff port. The component defines an internal error event named fail mapped to the ACCFail fault mode, with an occurrence probability of 1.3E-6. The AuxClimbControl.sensor1 implementation adds outbound error propagation on the controlsurfacecmd port, supporting two error types: ContinuousBadACCControl representing sustained incorrect control output, and ServiceOmission representing missing control output. Its internal error state machine, built on the ACCStates behavior definition from acemlib, defines a transition from the operational state to the continuousbadcontrol state when BadValue or ServiceOmission errors are received on the aoa1 port. Propagation rules specify that when in the continuousbadcontrol state, if a NoACCTurnOff error is received on the ACCOnOff port, a ContinuousBadACCControl error is propagated out the controlsurfacecmd port; in all operational states, if the ACCFail error event occurs, a ServiceOmission error is propagated out the controlsurfacecmd port. The pilot abstract component exposes four external features: one in feature port named discrepancylight for receiving angle-of-attack discrepancy warning light signals, one in feature port named ACCStandbyIndicator for receiving ACC standby status signals, one out feature port named controlsurfacecmd for transmitting pilot control inputs to the flight surface, and one out feature port named ACCOnOff for transmitting ACC on/off control commands. The pilot.nominal implementation accepts inbound ServiceOmission errors on the discrepancylight port, and propagates two outbound error types: NoPilotControl representing absence of valid pilot control input on the controlsurfacecmd port, and NoACCTurnOff representing failure to issue an ACC shutdown command on the ACCOnOff port. The implementation defines an internal error event set named mistakes, covering four fault modes: NoACCKnowledgeNoTurnoff representing failure to shut down ACC due to lack of ACC operation knowledge, AOADiscrepancyUnawareNoTurnoff representing failure to shut down ACC when the discrepancy warning is unavailable, AOADiscrepancyAwareNoTurnoff representing failure to shut down ACC even when the discrepancy warning is active, and PilotFlightControlMistake representing erroneous pilot flight control input. Error propagation rules for the nominal pilot specify that a NoACCTurnOff error is sent on the ACCOnOff port when either an AOADiscrepancyAwareNoTurnoff event occurs, or a ServiceOmission error on the discrepancylight port coincides with an AOADiscrepancyUnawareNoTurnoff event; a NoPilotControl error is sent on the controlsurfacecmd port when a PilotFlightControlMistake event occurs. Occurrence probabilities for pilot error events are set to 1.0E-6 for PilotFlightControlMistake, 1.0E-3 for AOADiscrepancyUnawareNoTurnoff, and 1.0E-6 for AOADiscrepancyAwareNoTurnoff. The pilot.NoACCKnowledge implementation extends the nominal pilot logic, modifying the NoACCTurnOff propagation rule to trigger when either a NoACCKnowledgeNoTurnoff event occurs, or a ServiceOmission error on the discrepancylight port coincides with an AOADiscrepancyUnawareNoTurnoff event; the NoACCKnowledgeNoTurnoff event has an occurrence probability of 1.0. The flightsurface device exposes three external features: one in feature port named autocmd for receiving automatic control commands from the ACC, one in feature port named pilotcmd for receiving manual control commands from the pilot, and one out feature port named flightsurfaceeffect for transmitting actuation output of the flight surface. The device accepts inbound ServiceOmission and ContinuousBadACCControl errors on the autocmd port, and inbound NoPilotControl errors on the pilotcmd port, while propagating outbound Incident errors representing hazardous flight events on the flightsurfaceeffect port. The device defines an internal error event named FlightSurfaceFailure representing inherent hardware failure of the flight surface, with an occurrence probability of 2.0E-9. Its internal error state machine, built on the ClimbControlStates behavior definition from acemlib, initializes in the ACCInCharge state where ACC has primary control authority; a transition to the PilotInCharge state occurs when a ServiceOmission error is received on the autocmd port. Error propagation rules specify that when in the PilotInCharge state, a NoPilotControl error on the pilotcmd port triggers an outbound Incident error on the flightsurfaceeffect port; when in the ACCInCharge state, a ContinuousBadACCControl error on the autocmd port triggers an outbound Incident error on the flightsurfaceeffect port; in all states, occurrence of the FlightSurfaceFailure event triggers an outbound Incident error on the flightsurfaceeffect port. The aoadiscrepancydetector device exposes three external features: two in data ports named aoa1 and aoa2 for receiving angle-of-attack readings from two separate sensors, and one out feature port named discrepancylight for transmitting discrepancy warning signals to the pilot. The device accepts inbound BadValue and ServiceOmission errors on both aoa1 and aoa2 ports, and propagates outbound ServiceOmission errors representing missing warning output on the discrepancylight port. The device defines an internal error event named DiscrepancyDetectorFailure representing functional failure of the monitoring unit, with an occurrence probability of 1.0E-6; propagation rules specify that in all states, occurrence of this failure event triggers a ServiceOmission error on the discrepancylight port. The aoadiscrepancydetector.permanentFail implementation adjusts the occurrence probability of the DiscrepancyDetectorFailure event to 1.0, representing permanent, guaranteed failure of the detector. The Engine device exposes a single out feature port named thrust for transmitting propulsion thrust output, which propagates outbound Incident errors representing propulsion-related hazardous events. The engine defines an error flow source named engineFailure tied to the thrust port, with an Incident occurrence probability of 1.5E-6. The top-level ac system exposes a single out feature port named aceffect for transmitting overall aircraft operational status, which propagates outbound Incident errors representing aircraft-level hazardous events. The ac.common implementation defines top-level error propagation logic, where an Incident error is sent on the aceffect port when either the flight surface propagates an Incident error, or both engine instances simultaneously propagate Incident errors on their thrust ports.

Data and signal flow across the system follows point-to-point connection paths defined for each system implementation. For the base ac.common implementation, the subcomponents include one aoasensor instance named aoa1, one flightsurface device instance, one AuxClimbControl.sensor1 instance named ACC, one pilot.nominal instance named pilot, and two Engine instances named engine1 and engine2. The defined flow paths are as follows: the aoareading output of the aoa1 sensor transmits angle-of-attack measurement data to the aoa1 input port of the ACC instance; the controlsurfacecmd output of the ACC instance transmits automatic flight control commands to the autocmd input of the flightsurface instance; the controlsurfacecmd output of the pilot instance transmits manual flight control commands to the pilotcmd input of the flightsurface instance; the ACCOnOff output of the pilot instance transmits ACC shutdown commands to the ACCOnOff input of the ACC instance; the flightsurfaceeffect output of the flightsurface instance transmits surface actuation outcomes to the top-level aceffect port of the ac system; the thrust outputs of engine1 and engine2 transmit propulsion output outcomes directly to the top-level aceffect port. Two sets of interface points remain unconnected across all ac system implementations: the aoa2 input data port of the ACC instance, and the paired ACCStandbyIndicator output port of the ACC instance and ACCStandbyIndicator input port of the pilot instance, with no valid data, signal, or error propagation routed to or from these unconnected endpoints. The ac.OneSensorSpec implementation extends the common implementation by adding one aoasensor instance named aoa2 and one standard aoadiscrepancydetector instance named aoaDiscrepancyIndicator, retaining all existing flow paths from the common implementation and adding three additional flow paths: the aoareading output of the existing aoa1 sensor transmits a parallel copy of angle-of-attack data to the aoa1 input of the discrepancy detector; the aoareading output of the newly added aoa2 sensor transmits angle-of-attack measurement data to the aoa2 input of the discrepancy detector; the discrepancylight output of the discrepancy detector transmits warning signals to the discrepancylight input of the pilot instance. The ac.OSSPermanentDiscrepancyFail implementation retains identical flow paths to the OneSensorSpec implementation, with no changes to connection endpoints, only refining the aoaDiscrepancyIndicator subcomponent to use the aoadiscrepancydetector.permanentFail implementation. The ac.OSSNoACCKNowledge implementation also retains identical flow paths to the OSSPermanentDiscrepancyFail implementation, with no changes to connection endpoints, only refining the pilot subcomponent to use the pilot.NoACCKnowledge implementation. All connections carry both valid functional data and signals, as well as associated error propagations between connected endpoints, with no signal transformation, filtering, or value conversion applied along connection paths.

All data and feature transmissions across connections follow an immediate, zero-delay transfer model, with no buffering, queueing, or arbitration delays introduced between sending and receiving endpoints. Error events across all components are assumed to occur independently per the defined occurrence probability distributions, with no time-based triggering constraints, minimum inter-arrival time requirements, or scheduled fault injection windows specified. State transitions triggered by inbound error events occur instantaneously upon error reception, with no transitional state hold time or processing delay defined for error handling logic. No mode switching latency, fault detection timeout, or operator response time requirements are specified for system functions.

All signals transmitted across feature ports, including ACC switch commands, flight control commands, status indicators, warning signals, actuation effects, and thrust outputs, use generic unstructured feature types with no dedicated message format, payload definition, or protocol overhead requirements. The system does not define dedicated bus components for inter-component communication. All inter-component connections are implemented as direct point-to-point bindings, with no bus access arbitration, protocol encapsulation, error correction coding, or bus-level fault containment mechanisms applied to transmitted data or signals. No access control rules or priority-based transmission scheduling are defined for inter-component communication paths.
