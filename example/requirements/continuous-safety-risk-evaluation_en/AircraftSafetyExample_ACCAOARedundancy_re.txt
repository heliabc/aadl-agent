The system shall be encapsulated within the AADL package named AircraftSafetyExample::ACCAOARedundancy. This package shall establish formal dependencies on two peer packages under the AircraftSafetyExample namespace: AircraftSafetyExample::AOADiscrepancy and AircraftSafetyExample::AOAVendors. The package shall import all public component, data, property, and annex definitions from both referenced packages, and expose all imported definitions as locally accessible elements via rename declarations to support unqualified name references within local component definitions. The package shall contain two specialized abstract component implementations and three layered system implementations to model a redundant dual-sensor Auxiliary Climb Control (ACC) architecture for aircraft safety. The first abstract component implementation is pilot.ACCStandbyIndicator, which extends the base pilot component type to model pilot interaction with ACC standby status indication and associated fault effects. The second abstract component implementation is AuxClimbControl.sensor2, which extends the base AuxClimbControl component type to model dual-sensor ACC operational logic and fault handling behavior. The base dual-sensor system implementation is ac.TwoSensorSpec, which extends the shared ac.common system implementation to add a second angle-of-attack (AOA) sensor and refine core ACC and pilot subcomponents to their fault-aware implementations. Two vendor-specific system variants shall extend ac.TwoSensorSpec to support homogeneous sensor configurations: ac.TwoSensorVA, which configures both AOA sensors to the vendorA sensor implementation, and ac.TwoSensorVB, which configures both AOA sensors to the vendorB sensor implementation.

All component interfaces shall align with inherited type definitions from base components and imported packages, with explicit error propagation interfaces defined for fault behavior modeling. The pilot.ACCStandbyIndicator abstract implementation shall define two error propagation points: an inbound propagation point named ACCStandbyIndicator that accepts ServiceOmission error states representing failure of the ACC standby status indication to reach the pilot, and an outbound propagation point named controlsurfacecmd that transmits NoPilotControl error states representing erroneous pilot control inputs to aircraft control surfaces. The component shall declare one internal error event named mistakes, mapped to the ACCFailUnawareFlightControlMistake error type, which represents pilot flight control errors caused by lack of awareness that ACC has entered standby mode. The AuxClimbControl.sensor2 abstract implementation shall define three error propagation points: an inbound propagation point named aoa2 that accepts BadValue and ServiceOmission error states representing invalid or missing measurements from the second AOA sensor, an outbound propagation point named ACCStandbyIndicator that transmits ServiceOmission error states representing failure of the ACC standby indication output to the pilot interface, and an outbound propagation point named controlsurfacecmd that transmits ServiceOmission error states representing loss of ACC control output to aircraft control surfaces. The component shall declare two internal error events: an approxvalue event mapped to the SymmetricApproximateValue error type for future symmetric sensor fault handling logic, and a standbyindicatorfail event representing internal failure of the standby indication output circuit. The component shall reference the ACCStates error behavior state machine from the acemlib library to track operational and standby operational modes. For system subcomponent structure, the ac.TwoSensorSpec implementation shall instantiate a second AOA sensor device named aoa2 typed to the base aoasensor device definition, refine the inherited ACC subcomponent to the AuxClimbControl.sensor2 implementation, and refine the inherited pilot subcomponent to the pilot.ACCStandbyIndicator implementation. The ac.TwoSensorVA implementation shall refine both the inherited aoa1 subcomponent and the local aoa2 subcomponent to the aoasensor.vendorA device implementation. The ac.TwoSensorVB implementation shall refine both the inherited aoa1 subcomponent and the local aoa2 subcomponent to the aoasensor.vendorB device implementation.

All inter-component signal flow within the dual-sensor architecture shall be implemented via unidirectional port-to-port connections, with all connections inherited from the ac.common base system retained without modification. Two new connections shall be defined in ac.TwoSensorSpec to support the second sensor and status indication flow. The first connection, designated a2, shall route valid AOA measurement data and associated error states from the aoareading output port of the aoa2 sensor device to the aoa2 input port of the ACC subcomponent. The second connection, designated accstandby, shall route valid ACC standby status signals and associated error states from the ACCStandbyIndicator output feature of the ACC subcomponent to the ACCStandbyIndicator input feature of the pilot subcomponent. Signal flow for the first AOA sensor, pilot control outputs, and ACC control surface commands shall follow the paths defined in the ac.common base implementation, with the second AOA sensor providing redundant measurement input to the ACC fault detection logic.

Component error behavior and state transitions shall follow deterministic triggering rules aligned with fault detection logic. The AuxClimbControl.sensor2 component shall execute an immediate state transition from operational mode to standby mode when one or more qualifying faults are detected on either aoa1 or aoa2 input interfaces, where qualifying faults include BadValue and ServiceOmission error states. Upon triggering this transition to standby mode, the component shall immediately propagate a ServiceOmission error on the controlsurfacecmd output interface to signal transfer of control authority from ACC to the pilot. If the internal standbyindicatorfail error event occurs at any point during operation, the component shall immediately propagate a ServiceOmission error on the ACCStandbyIndicator output interface, blocking delivery of standby status notification to the pilot. The pilot.ACCStandbyIndicator component shall propagate a NoPilotControl error on the controlsurfacecmd output interface only when two concurrent conditions are met: a ServiceOmission error is present on the inbound ACCStandbyIndicator interface indicating the pilot did not receive standby notification, and the internal ACCFailUnawareFlightControlMistake error event occurs indicating the pilot made an erroneous control input due to unawareness of ACC status. The occurrence probability of the standbyindicatorfail event in AuxClimbControl.sensor2 shall be set to 1.0E-9 per operational exposure. The occurrence probability of the ACCFailUnawareFlightControlMistake event in pilot.ACCStandbyIndicator, under the condition of missing ACC standby indication, shall be set to 1.0E-3 per operational exposure to reflect elevated pilot error risk when status feedback is unavailable. No explicit end-to-end latency values or periodic scheduling offsets are defined within this package; all scheduling and latency requirements inherited from the ac.common base implementation shall remain in effect, with error propagation and state transitions executed within the same processing cycle as the triggering fault event.

All error model types used across component implementations shall be sourced from standardized libraries: core error types including ServiceOmission and BadValue shall be referenced from the ErrorLibrary, while domain-specific error types including ACCFailUnawareFlightControlMistake and SymmetricApproximateValue, plus the ACCStates behavior state machine, shall be referenced from the acemlib library. AOA sensor measurement data types shall conform to the interface specifications defined in the imported AOAVendors package, with vendorA and vendorB sensor implementations adhering to the base aoasensor data interface to support interchangeable configuration in the VA and VB system variants without requiring changes to connected ACC component logic. No dedicated communication bus components shall be defined within this package; all inter-component communication shall use direct port-to-port connections for transmission of sensor data, control commands, status signals, and associated error state information. All communication protocol, bus access, and data encoding rules inherited from the ac.common base implementation and imported packages shall apply without modification to connections defined in this package.
