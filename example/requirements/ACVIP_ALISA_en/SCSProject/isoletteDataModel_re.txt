The system is organized under a single root AADL package named isoletteDataModel, with public visibility applied to all contained type and component definitions. The root package declares explicit import dependencies on five external packages: the Data_Model package, which provides standardized data modeling property definitions for consistent type constraint enforcement; the thermostat package, which provides executable implementations of the thermostat control subsystem; the heat_source package, which provides executable implementations of the heat output device; the temperature_sensor package, which provides executable implementations of the ambient temperature measurement device; and the operator_interface package, which provides executable implementations of the user interaction subsystem. All shared data definitions and top-level system integration logic are encapsulated directly within the isoletteDataModel package, with no nested sub-packages defined in the current scope. The top-level system component contained in the package is isoletteSystem, which represents the complete integrated isolette thermal regulation system, with a single implementation named isoletteSystem.impl that defines the first-tier component composition and interconnection logic for the full system.

The top-level isoletteSystem component type does not define any externally exposed ports, as all functional interactions are contained between internal subcomponents, with no external system interfaces specified in the current package scope. The isoletteSystem.impl implementation instantiates four first-tier subcomponents, each aligned with a component type provided by the imported external packages. The first subcomponent is named thermostat, typed as the thermostat subsystem implementation provided by the thermostat package, which exposes four data ports for cross-component interaction: an inbound data port for current temperature measurements, an outbound data port for heat control commands, an inbound data port for operator configuration settings, and an outbound data port for system status feedback to the operator. The second subcomponent is named temperature_sensor, typed as the temperature sensor device implementation provided by the temperature_sensor package, which exposes a single outbound data port for sampled current temperature measurements. The third subcomponent is named heat_source, typed as the heat source device implementation provided by the heat_source package, which exposes a single inbound data port for heat actuation commands. The fourth subcomponent is named operator_interface, typed as the operator interface subsystem implementation provided by the operator_interface package, which exposes two data ports for cross-component interaction: an outbound data port for user-entered configuration settings, and an inbound data port for system status feedback to be presented to the user. For contained data components, the operator_feedback data type defines an implementation that includes four internal data subcomponents to structure feedback payloads: a regulator_status field, a monitor_status field, a display_temperature field, and an alarm field. No data components define externally exposed ports, as all data types are used exclusively as structured payloads for port-based communication between system components.

All inter-component data exchange within the integrated isoletteSystem is routed via direct unidirectional point-to-point data port connections defined in the isoletteSystem.impl implementation, with no intermediate routing components between connected endpoints. The first data flow path originates at the temperature_sensor subcomponent, where sampled current temperature data is transmitted from the sensor’s outbound current_temperature port to the matching inbound current_temperature port on the thermostat subcomponent, delivering real-time temperature measurements to the core control logic. The second data flow path originates at the operator_interface subcomponent, where user-entered configuration settings are transmitted from the interface’s outbound operator_settings port to the matching inbound operator_settings port on the thermostat subcomponent, delivering user-defined setpoints and alarm thresholds to the control logic. The third data flow path originates at the thermostat subcomponent, where generated heat actuation commands are transmitted from the thermostat’s outbound heat_control port to the matching inbound heat_control port on the heat_source subcomponent, delivering binary control signals to adjust heat output to maintain desired temperature levels. The fourth data flow path originates at the thermostat subcomponent, where compiled system status, temperature readout, and alarm state data is transmitted from the thermostat’s outbound operator_feedback port to the matching inbound operator_feedback port on the operator_interface subcomponent, delivering updated system state information for presentation to the end user. No circular data paths are defined in the top-level system integration, with all flows following a unidirectional path from sensing and user input components to the central thermostat control subsystem, then from the control subsystem to the heat source actuation component and user output interface.

The isoletteDataModel package does not define explicit timing, scheduling, or latency constraints at the top system integration layer. No thread, process, virtual processor, or processor components are declared within the package scope, meaning all execution timing rules, dispatch protocols, scheduling partition assignments, component execution periods, deadline requirements, and end-to-end latency budgets are encapsulated within the imported external component packages for the thermostat, temperature_sensor, heat_source, and operator_interface subsystems and devices. No cross-component timing synchronization requirements, transmission delay limits, or jitter constraints are specified for the point-to-point port connections defined in the top-level system implementation, as these timing properties are deferred to the lower-level implementation details of each connected component.

No dedicated communication bus, virtual bus, or bus access components are defined within the isoletteDataModel package. All inter-component data exchange is implemented via the direct point-to-point data port connections previously described, with no intermediate bus routing, protocol encapsulation, or shared communication media defined in the current integration scope. All data transmitted across these port connections must strictly conform to the shared data type definitions contained in the package, with type conformance enforced at connection binding time. All data type constraints are specified using properties from the imported Data_Model package to ensure consistent representation and valid value ranges across all system components. Three base enumerated data types are defined for general use across the system. The first enumerated type is valid_flag, which uses an enum data representation with two allowed enumerator values: Invalid and Valid, used to indicate the trustworthiness and validity of associated measurement or configuration data. The second enumerated type is on_off, which uses an enum data representation with two allowed enumerator values: On and Off, used to represent binary actuation states and alarm activation states. The third enumerated type is status, which uses an enum data representation with two allowed enumerator values: Ok and Error, used to represent the operational health state of functional control and monitoring modules. Two base real-valued range types are defined for temperature data, with measurement units specified as degrees Fahrenheit. The first real type is measured_temperature_range, which enforces a valid real number range of 68.0 to 105.0 for raw temperature sensor measurements. The second real type is temperature_range, which enforces a base valid real number range of 0.0 to 105.0, with five specialized implementations that narrow the valid range for specific use cases: the measured_temperature_range implementation narrows the range to 68.0 to 105.0 as a subtype of the generic temperature_range, the lower_desired_range implementation narrows the range to 97.0 to 99.0 for user-configured lower temperature setpoints, the upper_desired_range implementation narrows the range to 98.0 to 100.0 for user-configured upper temperature setpoints, the lower_alarm_range implementation narrows the range to 93.0 to 98.0 for lower temperature alarm thresholds, and the upper_alarm_range implementation narrows the range to 99.0 to 103.0 for upper temperature alarm thresholds. Composite and structured data types are defined to package related data elements for port transmission and internal storage. The first composite data type is current_temperature, which defines two named elements without an explicit struct data representation marker: a temperature value element constrained to the top-level measured_temperature_range real type, and a validity status element constrained to the valid_flag enumerated type, intended for direct use as the payload for the current temperature sensor data port between the temperature sensor and thermostat. The second structured type is temperature, which explicitly uses a struct data representation with two named elements: a temperature value element constrained to the base temperature_range real type, and a validity status element constrained to the valid_flag enumerated type, used as the generic temperature type for setpoints, alarm thresholds, and user display values, with five specialized implementations that bind the temperature value element to specific range types: the current_temperature_impl implementation binds the temperature value element to the top-level measured_temperature_range real type for transmission of current sensor readings in generic temperature struct format, the lower_desired_temperature implementation binds the temperature value element to the temperature_range.lower_desired_range implementation for lower setpoint storage and transmission, the upper_desired_temperature implementation binds the temperature value element to the temperature_range.upper_desired_range implementation for upper setpoint storage and transmission, the lower_alarm_temperature implementation binds the temperature value element to the temperature_range.lower_alarm_range implementation for lower alarm threshold storage and transmission, and the upper_alarm_temperature implementation binds the temperature value element to the temperature_range.upper_alarm_range implementation for upper alarm threshold storage and transmission. Three top-level communication payload data types are defined for cross-component port exchange. The first payload type is heat_control, with a single implementation named heat_control.impl that binds the type’s base value to the on_off enumerated type, to carry binary heat source activation and deactivation commands between the thermostat and heat source. The second payload type is operator_settings, defined as an abstract data type for carrying user configuration values between the operator interface and thermostat, with no internal structure or implementation defined in the current package scope, as structure details are deferred to the connected component implementations. The third payload type is operator_feedback, with a single implementation named operator_feedback.impl that defines four internal data fields to structure status reports: a regulator_status field typed as the status enumerated type to report the health of the temperature regulation function, a monitor_status field typed as the status enumerated type to report the health of the temperature monitoring function, a display_temperature field typed as the generic temperature structured type to carry the current measured temperature for user display, and an alarm field typed as the dedicated alarm data type to carry current alarm state. The alarm data type is defined as a dedicated type that binds its base value to the on_off enumerated type, to represent binary alarm activation and deactivation states for user notification.
