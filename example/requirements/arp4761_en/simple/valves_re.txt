The top-level modeling namespace is defined as the valves public package, which declares explicit import dependencies on two external supporting packages: the base_types package containing core primitive data type definitions, and the common package containing shared communication bus interface and structured command data type definitions. All component definitions within the valves package are contained in the public package section to support unqualified external reference. The package defines a hierarchy of system component types structured through type extension to maximize reuse of common valve and selector functionality, paired with corresponding implementation definitions for instantiable component types. The root generic system type forms the base abstraction for all inline pressure path valve components, with three directly extended subtypes: the generic_pwm_input system type that adds PWM control input capability, the boolean_shutoff system type that adds binary boolean shutoff control input, and the cmd_shutoff system type that adds structured skid command input for command-driven shutoff operation. A separate root selector system type forms the base abstraction for multi-source pressure selection components, with two directly extended subtypes: the selector_basic system type that provides a single combined selected pressure output, and the selector_detailed system type that provides independent split pressure outputs for dual channel distribution. Instantiable system types are paired with empty implementation definitions suffixed with .i, including generic.i, generic_pwm_input.i, and selector.i, with no internal subcomponents, connections, or private behavior defined for these implementations at the current abstraction level.

The base generic valve system type defines two bus access interfaces aligned with pressure signal transfer: a required bus access port named input for connection to upstream pressure supply via the common::pressure.i bus interface, and a provided bus access port named output for connection to downstream pressure consumers via the common::pressure.i bus interface. Error propagation semantics for the generic valve, defined using the error type set from the shared error_library and the standard simple error behavior model from that library, define that the input port accepts incoming NoService error propagations, the output port transmits outgoing NoService error propagations, and a direct error flow path maps NoService errors received at the input port to immediate propagation out of the output port. The generic_pwm_input system type inherits all interfaces and error propagation rules from the generic base type, and adds one additional required bus access port named input_pwm for connection to PWM control sources via the common::pwm.generic bus interface, with no additional error propagation rules defined for this added interface at the type level. The boolean_shutoff system type inherits all interfaces and error propagation rules from the generic base type, and adds one additional incoming data port named boolean_input that carries Base_Types::Boolean values for binary shutoff control, with no additional error propagation rules defined for this added interface at the type level. The cmd_shutoff system type inherits all interfaces and error propagation rules from the generic base type, and adds one additional incoming data port named cmd_input that carries common::command.skid values for skid command-driven shutoff control. Error propagation rules for cmd_shutoff, defined using the error type set from the shared error_library and the standard simple error behavior model from that library, define that the cmd_input port accepts incoming NoValue error propagations, with two dedicated error flow paths: one path maps NoValue errors received at cmd_input to NoService error propagation out of the output port, and a second path defines an internal error source capable of generating NoService errors directly on the output port. The error behavior state machine for cmd_shutoff defines two failure transitions from the initial Operational state: a transition to the Failed state triggered by reception of a NoValue error on the cmd_input port, and a transition to the Failed state triggered by reception of a NoService error on the inherited input pressure port. When operating in the Failed state, the cmd_shutoff component unconditionally propagates a NoService error out of the inherited output pressure port. The base selector system type defines three required bus access ports for incoming pressure supply connections, all interfacing to the common::pressure.i bus: accumulator_input for connection to the accumulator pressure source, green_input for connection to the green system pressure source, blue_input for connection to the blue system pressure source. The base selector also defines three incoming data ports for control input: select_alternate carrying Base_Types::Boolean values to trigger alternate source selection, cmd_nor carrying common::command.skid values for normal operating mode commands, and cmd_alt carrying common::command.skid values for alternate operating mode commands. Error propagation rules for the base selector, defined using the error type set from the shared error_library, define that all three pressure input ports accept incoming NoService error propagations, and all three control data ports accept incoming NoValue error propagations. Three error sink flows are defined for the base selector, which terminate NoValue errors received on the cmd_nor, cmd_alt, and select_alternate ports within the component without direct propagation to other interfaces at the base type level. The selector_basic system type inherits all interfaces and error propagation rules from the base selector type, and adds one provided bus access port named output for connection to downstream consumers via the common::pressure.i bus interface. Additional error propagation rules for selector_basic, defined using the error type set from the shared error_library, define that the output port transmits outgoing NoService error propagations, with three direct error flow paths mapping NoService errors received on the green_input, blue_input, and accumulator_input ports respectively to NoService error propagation out of the output port. The selector_detailed system type inherits all interfaces and error propagation rules from the base selector type, and adds two provided bus access ports for dual channel pressure delivery, both interfacing to the common::pressure.i bus: green_output for the green distribution channel, and blue_output for the blue distribution channel. Additional error propagation rules for selector_detailed, defined using the error type set from the shared error_library and the standard simple error behavior model from that library, define that both green_output and blue_output ports transmit outgoing NoService error propagations, supported by eight dedicated error flow paths: NoService errors received on green_input propagate to green_output, NoService errors received on blue_input propagate to blue_output, NoService errors received on accumulator_input propagate to both green_output and blue_output, NoValue errors received on cmd_alt propagate as NoService errors out of blue_output, NoValue errors received on cmd_nor propagate as NoService errors out of green_output, and NoValue errors received on select_alternate propagate as NoService errors out of both green_output and blue_output. The error behavior state machine for selector_detailed defines three failure transitions from the initial Operational state: a transition to the Failed state triggered by reception of a NoValue error on the select_alternate port, a transition to the Failed state triggered by reception of a NoValue error on the cmd_alt port, and a transition to the Failed state triggered by reception of a NoValue error on the cmd_nor port. When operating in the Failed state, the selector_detailed component unconditionally propagates NoService errors out of both the green_output and blue_output ports.

Functional data flow across all valve components derived from the generic base type follows a core path that transfers pressure signaling from the upstream required input pressure bus access to the downstream provided output pressure bus access, with flow modulation applied via component-specific control inputs. For the generic_pwm_input valve variant, PWM control signals received via the input_pwm bus access are used to modulate the magnitude of pressure passed from the input to output pressure path. For the boolean_shutoff valve variant, binary state values received via the boolean_input data port are used to toggle between fully open pressure passage and fully closed pressure shutoff between the input and output pressure ports. For the cmd_shutoff valve variant, structured skid command values received via the cmd_input data port are used to control pressure passage or shutoff between the input and output pressure ports, with a defined fail-safe state that fully blocks pressure delivery to the output port when valid command input is lost or valid incoming pressure supply is lost. Functional data flow across all selector components follows a core path that routes pressure from one or more of the three incoming pressure supply inputs to component outputs, with source selection determined by the state of received control inputs. For the selector_basic variant, pressure from the selected source, chosen based on the boolean state of the select_alternate input and the content of received cmd_nor and cmd_alt skid commands, is routed to the single output pressure port as a unified supply with no split between separate distribution channels. For the selector_detailed variant, pressure from selected sources is routed independently to the two output channels: the green_output path is supplied by the green_input and accumulator pressure sources, with gating control applied via the cmd_nor input, and the blue_output path is supplied by the blue_input and accumulator pressure sources, with gating control applied via the cmd_alt input, while cross-channel source switching is triggered by the state of the select_alternate control signal. Error flows across all components with defined error behavior follow predefined propagation paths separate from functional flow, where lost service on pressure inputs or lost value on control inputs triggers predefined error propagation to downstream interfaces or component failure state transitions as specified per component type.

At the current abstraction level, no explicit scheduling rules, execution time budgets, deadline constraints, or end-to-end latency limits are defined for any component within the valves package. All components are modeled as system-level abstractions without decomposition into executable thread or process subcomponents, so no periodic or aperiodic dispatch rules, priority assignments, or processor binding requirements are specified. Error propagation and state transition behavior is defined as logically immediate, with no specified time delay between error reception, state transition execution, and error propagation to downstream interfaces. No clock synchronization or time-triggered communication requirements are defined for bus or data port interactions.

All communication bus interfaces referenced by components in the valves package are imported from the external common package, with strict type matching enforced for all bus access connections. The common::pressure.i bus type is designated for all pressure signal transfer paths, used exclusively for connections between upstream pressure sources, valve components, selector components, and downstream pressure consumers. The common::pwm.generic bus type is designated for PWM control signal transfer, used exclusively for connections between PWM control sources and the input_pwm port of the generic_pwm_input valve variant. Bus access direction follows a consistent rule: required bus access ports are used for all incoming bus connections, where the component acts as a bus access requester connecting to an upstream bus provider, and provided bus access ports are used for all outgoing bus connections, where the component acts as a bus provider for downstream connected components. All data port values use types imported from external packages, with strict type matching enforced for all data port connections. The Base_Types::Boolean primitive data type is designated for binary state control signals, used for both the boolean shutoff input on boolean_shutoff valves and the alternate selection input on selector components. The common::command.skid structured data type is designated for skid control command signals, used for both the command input on cmd_shutoff valves and the normal and alternate command inputs on selector components. All data ports are defined as unidirectional incoming ports, with no outgoing data ports specified on any valve or selector component at the current abstraction level. Error type definitions for components with specified error behavior are imported from the external error_library, with components that include state-based failure logic utilizing the predefined simple error behavior model that defines Operational and Failed component states. Two standard error tokens are used across applicable components: the NoService error token, which indicates loss of valid pressure signal transfer and is only propagated across pressure bus interfaces with explicitly defined error propagation rules, and the NoValue error token, which indicates loss of valid data content and is only propagated across control data ports with explicitly defined error propagation rules. Defined error mapping rules specify that incoming NoValue errors on control ports with defined error propagation may trigger component failure and subsequent outgoing NoService errors on pressure output ports, with no reverse mapping of NoService errors on pressure ports to NoValue errors on control ports defined for any component.
