The entire modeled domain is encapsulated within a public package named power. The power package shall declare explicit dependencies on three external packages to support cross-package element referencing: the common package for shared generic resource definitions, the ARP4761 package for aviation safety assessment standard property definitions, and the EMV2 package for error modeling annex semantic definitions. Two top-level component types shall be defined within the power package: a device component typed as battery, and a system component typed as power. Each component type shall be paired with one generic implementation variant, specifically battery.generic for the battery device type, and power.generic for the power system type. The battery component shall act as a leaf-level hardware device module with no nested subcomponents in its implementation. The power component shall act as an aggregate system-level module that depends on the battery component type to construct its internal subcomponent structure.

The battery device component shall define a single external feature: a provided bus access port named socket, which conforms to the generic power bus type defined as common::power.generic. The battery component shall implement EMV2 error model constructs, which import type definitions from the standard error_library, and import the simple error behavior definitions from error_library to support state machine specification. The battery component shall define error propagation interfaces aligned with EMV2 semantics, where the socket port supports outward propagation of the NoPower error, with a defined error source path f1 that sources the NoPower error directly at the socket port. The battery component shall define internal error behavior constructs including two distinct error events: the Depleted event representing total battery charge exhaustion, and the Explode event representing catastrophic battery structural failure. The battery component shall have two discrete operational states for error behavior: the Operational state representing nominal functional status, and the Failed state representing loss of intended function. State transition rules for the battery component shall specify that a transition from the Operational state to the Failed state is triggered by either the Depleted error event or the Explode error event. Error propagation rules tied to component state shall specify that when the component resides in the Operational state, the socket port propagates a NoError status via propagation path normal, and when the component resides in the Failed state, the socket port propagates the NoPower error via propagation path p1. The battery.generic device implementation shall not define additional subcomponents, internal connections, or extended features, and shall fully inherit all interface and behavior definitions from the battery component type. The power system component shall define two external provided bus access ports, named line1 and line2 respectively, both of which conform to the common::power.generic power bus type. The power.generic system implementation shall define two internal subcomponents, both instantiated from the battery.generic device type, named battery1 and battery2 respectively. The power.generic implementation shall define two bidirectional bus access connections: the connection named pwr1 shall link the socket port of the battery1 subcomponent to the external line1 port of the power system, and the connection named pwr2 shall link the socket port of the battery2 subcomponent to the external line2 port of the power system. No additional internal connections or cross-links between subcomponents shall be defined in the power.generic implementation.

Power supply as the core transmitted entity shall flow along the bidirectional bus access paths within the power system. External power-consuming loads connected to the power system shall receive power supply from the battery1 subcomponent via the line1 external port, through the direct connection between battery1.socket and line1, and shall receive power supply from the battery2 subcomponent via the line2 external port, through the direct connection between battery2.socket and line2. The two power supply paths shall be fully independent with no cross-over power flow, no intermediate power conversion, and no internal signal processing between subcomponent output ports and system external ports. Error states shall propagate along the same physical paths as nominal power flow. When either battery subcomponent transitions to the Failed state due to an internal error event, the associated NoPower error shall propagate sequentially from the subcomponent socket port, across the internal bus connection, to the corresponding external system line port, and onward to connected downstream loads. When a battery subcomponent remains in the Operational state, no error condition shall propagate along its connected supply path.

All components defined within the power package are hardware device and system constructs, with no defined thread, process, or other software executable units. As such, no periodic scheduling, event-triggered task scheduling, priority assignment, or execution deadline constraints shall apply to elements in the package. The power supply paths are persistent hardware conduction paths with no protocol-induced scheduling overhead. Error state propagation shall be strictly synchronous with component state transitions: immediately following a component state change triggered by an internal error event, the corresponding port error status shall be updated and propagated to all connected bus endpoints, with no intentional propagation delay configured.

All bus access ports defined within the power package shall reuse the pre-defined common::power.generic generic power bus type from the common package; no new bus types shall be defined locally within the power package. All bus access connections shall represent bidirectional hardware power delivery paths capable of supporting the electrical interface requirements of the generic power bus. Error types used in the EMV2 annex for the battery component shall be imported from the referenced external error library, including the NoError and NoPower error types, with no custom error data types defined locally within the power package. Safety and reliability property values shall be configured per defined rules: for the NoPower error propagated from the battery socket port, ARP4761 hazard properties shall be set to reference ARP4761 page 277 figure 9, describe the failure as loss of one power source with critical risk if both primary and redundant sources are lost, apply to the Landing and RTO flight phases, describe the effect as loss of electrical power to the BSCU, assign a FailureConditionClassification of Major, set a QualitativeProbabilityObjective of Probable, and note that dual power loss constitutes a major hazard. The EMV2 OccurrenceDistribution property for the socket.NoPower error shall be configured to use a Poisson distribution with a probability value of 1.35e-5. For the internal Explode error event of the battery component, ARP4761 hazard properties shall be set with a to-be-determined cross reference, describe the failure as battery explosion, apply to all flight phases, describe the effect as a major physical hazard, assign a FailureConditionClassification of Catastrophic, set a QualitativeProbabilityObjective of ExtremelyImprobable, and note that the failure causes physical impact to adjacent components. For the internal Depleted error event of the battery component, ARP4761 hazard properties shall be set with a to-be-determined cross reference, describe the failure as battery charge depletion, apply to all flight phases, describe the effect as total loss of stored battery power, assign a FailureConditionClassification of Major, set a QualitativeProbabilityObjective of Probable, and note that the failure becomes a system-level concern if the redundant battery also fails.
