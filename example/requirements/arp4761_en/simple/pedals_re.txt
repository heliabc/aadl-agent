The system shall establish a standalone public AADL package named pedals to encapsulate all pedal system component definitions. The pedals package shall declare formal import dependencies on three external supporting packages: the common package to access shared cross-system data type definitions, the EMV2 annex package to enable standardized error modeling constructs, and the ARP4761 annex package to support aviation safety assessment property assignments. Within the pedals package, a system component type named pedals shall be defined to represent the abstract pedal system interface and associated behavior, and a single concrete system implementation named pedals.generic shall be provided as a stub instantiation of the pedals system type, with no internal subcomponent decomposition specified in the current implementation.

The pedals system type shall define two identical outbound data port features as its complete external functional interface, designated signal1 and signal2. Both ports shall operate as unidirectional out ports carrying data to connected downstream components. The pedals.generic system implementation shall not define internal subcomponents, internal port connections, or internal feature mappings, consistent with its role as an initial stub component for early system architecture integration.

Nominal functional data flow for the pedals system shall consist of pedal command values generated within the component, transmitted outward across the system boundary via both signal1 and signal2 out ports, with no inbound data ports or incoming data flows required to support core pedal signal generation functionality. For error-related flow paths, the system shall define two explicit error source flows, labeled f1 and f2, which originate at the external interface of signal1 and signal2 respectively, to propagate defined error states from the pedals component to connected downstream elements without traversing internal subcomponent error paths. The defined error propagation for both ports shall carry the NoService error state when activated.

The pedals system shall implement a state-based error behavior model aligned with EMV2 specifications to govern fault response and state transitions. The system shall initialize in the fully functional Operational state at system start. A single discrete internal error event named InternalFault shall be defined as the sole trigger for fault-related state changes; upon occurrence of the InternalFault event, the system shall execute an immediate, unconditional transition from the Operational state to the Failed state. When operating in the Failed state, the system shall immediately and unconditionally propagate the NoService error condition out through both the signal1 and signal2 out ports, with no guard conditions or added delay applied to this error propagation. No explicit periodic or aperiodic task scheduling rules, port transmission latency budgets, or end-to-end flow timing constraints shall be specified for the current stub implementation of the pedals system, with such timing requirements reserved for subsequent detailed design refinement.

All functional data transmitted across the signal1 and signal2 out ports shall strictly conform to the pedal command data type defined at the common::command path within the imported common package, with no custom pedal-specific data types defined locally within the pedals package. No dedicated communication bus components or bus access features shall be defined within the pedals package, as direct port-to-port data communication is used for all external signal exchanges between the pedals component and connected downstream elements. The error model for the pedals component shall import the standardized error type set and simple error behavior definitions from the shared error_library to ensure consistent error state representation across the broader system model. Safety properties aligned with ARP4761 standards shall be applied to the NoService error propagation on both signal1 and signal2 ports, classifying the associated hazard as Hazardous with a qualitative probability objective of ExtremelyRemote. The documented hazard for this NoService condition describes a failure mode where no pedal signal is transmitted to downstream components, preventing the BSCU from generating valid brake control outputs, with an associated note that concurrent loss of both system power supplies would escalate the severity of this failure condition to critical. Hazard metadata fields including cross-reference identifiers and applicable operational flight phases shall be marked as TBD for population during later safety assessment activities. An EMV2 occurrence distribution property shall be assigned to the pedals system Failed state, specifying a fixed probability distribution with a probability value of 3.4e-5 for system entry into the Failed state due to internal fault occurrence.
