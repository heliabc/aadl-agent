The system shall define a standalone AADL package named pump, with all model elements declared in the package’s public scope accessible to external dependent models. The pump package shall declare three mandatory external package dependencies at the public level, consisting of the common package for shared interface and data type specifications, the ARP4761 package for civil aviation safety assessment property definitions, and the EMV2 package for error modeling annex capability support. The pump package shall not contain nested sub-packages, and all component type and implementation declarations shall reside within the public section of the package.

The pump package shall define a top-level system type named pump. The pump system shall expose a single provided bus access feature identified as pressure_output, which is bound to the pressure interface instance i defined in the common package. The pump system shall support outbound error propagation through the pressure_output feature, with NoService as the only propagable error state on this interface. A named error source flow named nopressure shall be defined for this error propagation path, marking the pressure_output interface as the origination point of NoService error for end-to-end error propagation analysis. A corresponding system implementation identified as pump.i shall be declared for the pump system type. The pump.i implementation shall not define internal subcomponents, internal features, port groups, or internal connection structures, forming a minimal leaf-level system implementation with no nested composition.

The pump system shall operate as a root source of pressure transmission service, delivering valid, error-free pressure service to externally connected components via the pressure_output provided bus access interface during normal functional operation. No internal data forwarding paths between subcomponents exist within the pump.i implementation, as all output service states are generated directly by the pump system’s own operational status rather than forwarded from internal sub-elements. When the pump enters a failed operational state, it shall immediately cease delivery of normal pressure service and transmit corresponding service failure status through the same pressure_output interface to connected downstream components.

The pump system shall implement a two-state component error behavior model, with the initial state set to Operational to represent normal, fully functional operation, and a terminal Failed state to represent complete loss of pump pressure delivery capability. The system shall define an internal error event named HydraulicError as the only trigger for state transition. When the pump is in the Operational state, occurrence of the HydraulicError event shall trigger an unconditional, zero-added-delay transition directly to the Failed state, with no intermediate processing states or transition guard conditions. The system shall enforce state-aligned output propagation rules at all times: when operating in the Operational state, the pressure_output interface shall continuously propagate the NoError status without service interruption or data corruption; when operating in the Failed state, the pressure_output interface shall continuously propagate the NoService status to indicate total loss of pressure delivery capability. Safety property constraints shall be applied to the HydraulicError event in compliance with ARP4761 requirements, with the hazard cross-reference mapped to ARP4761 page 275 figure L9, the failure scenario defined as hydraulic error occurring on a pump, applicable flight and operational phases marked as to be determined, failure effect described as loss of one pump unit, failure condition classification set to the Major hazard level, qualitative probability objective set to Probable, and supplementary annotation specifying that concurrent loss of both pump units constitutes a Major hazard. The error occurrence distribution for the HydraulicError event and the propagated NoService error on the pressure_output interface shall follow a Poisson distribution with a fixed probability value of 2.5e-5, per EMV2 occurrence property specifications.

The pump package shall not redefine, modify, or extend the pressure bus type and associated protocol used for the pressure_output interface, and shall fully reuse the pre-defined bus specification for the pressure.i instance imported from the common package. The pump system shall hold provider-level access permission to the connected pressure bus, granting it authority to drive bus state and transmit both normal service data and error status to all components connected as bus subscribers. No custom data type definitions shall be declared within the pump package, as all interface data formats and bus protocol specifications are sourced from imported external shared packages. The error behavior model for the pump system shall import all required error state types and the base simple error behavior rule set from the referenced error_library, with no local custom error type definitions or core behavior rule redefinitions beyond the specified HydraulicError event, associated state transitions, and propagation mappings.
