A public AADL package named impl::wheel is defined, with an explicit dependency on the common package to access publicly declared modeling elements from that package. The package declares an abstract root system type named wheel, which acts as the base classifier for all wheel component variants and contains no concrete feature declarations or internal structure definitions. A system type named wheel_one_input is defined as a direct extension of the base wheel type, intended to represent the wheel configuration that abstracts dual pressure supply channels into a single logical access point. A corresponding system implementation named wheel_one_input.i is declared for the wheel_one_input type, with no internal subcomponents, connections, or behavior declarations. A system type named wheel_two_inputs is defined as a direct extension of the wheel_one_input type, intended to represent the wheel configuration that explicitly models independent dual pressure supply channels. A corresponding system implementation named wheel_two_inputs.i is declared for the wheel_two_inputs type, with no internal subcomponents, connections, or behavior declarations. All error modeling constructs within the package reference error types and behavior definitions from the WBSImplementationErrorLib error library as required by EMV2 annex specifications.

The abstract root wheel system type exposes no external interaction interfaces. The wheel_one_input system type declares a single required bus access feature named input, which supports access to an external pressure supply bus. The EMV2 annex subclause for wheel_one_input imports error types from WBSImplementationErrorLib and applies the Twostate error behavior model from the same library. Within this error specification, the input feature is defined as an inbound propagation point for the NoService error, and NoService errors arriving at the input feature are designated as an error sink. The component error behavior for wheel_one_input defines two operational states: Operational to indicate normal functional operation, and Failed to indicate a loss of component function. A single state transition rule is specified: when a NoService error propagates into the component via the input feature, the component immediately transitions from the Operational state to the Failed state. The wheel_two_inputs system type inherits the input required bus access feature from its parent wheel_one_input type, and declares two additional required bus access features named green_input and blue_input, each supporting access to an independent external pressure supply bus. The EMV2 annex subclause declared for wheel_two_inputs fully replaces the EMV2 subclause inherited from wheel_one_input, and similarly imports error types from WBSImplementationErrorLib and applies the Twostate error behavior model. Within this custom error specification, the green_input and blue_input features are defined as inbound propagation points for the NoService error, and NoService errors arriving at each of these two features are designated as separate error sinks. Two state transition rules are specified for wheel_two_inputs: when a NoService error propagates into the component via the green_input feature, the component transitions from the Operational state to the Failed state; when a NoService error propagates into the component via the blue_input feature, the component transitions from the Operational state to the Failed state. No error propagation rules, error flow definitions, or state transition logic are defined for the inherited input feature within the wheel_two_inputs error specification. Both wheel system implementations declare no internal subcomponents, no internal interaction points, and no internal connection logic.

For the wheel_one_input configuration, all pressure-related interaction data flows into the wheel component from the connected external pressure bus exclusively through the input required bus access interface. The component does not transmit any outbound data or error events to external systems. All NoService error events received through the input interface terminate at the component boundary as a designated error sink, directly triggering the component state transition to the Failed state, with no onward error propagation to external entities. For the wheel_two_inputs configuration, pressure-related interaction data may flow into the wheel component from connected external pressure buses through the inherited input interface, as well as through the green_input and blue_input interfaces. The component does not transmit any outbound data or error events to external systems. Per the defined error specification, only NoService error events received through the green_input and blue_input interfaces terminate at the component boundary as designated error sinks, with each event capable of independently triggering the component state transition to the Failed state. No error handling, termination, or propagation rules are defined for events received through the inherited input interface in this configuration.

No periodic scheduling policies, execution time budgets, end-to-end latency requirements, thread priority assignments, or mode-triggered scheduling rules are declared for any system type or implementation within the package. All defined component state transitions follow an event-triggered execution paradigm, where transitions to the Failed state are activated immediately upon reception of a qualifying NoService error event at the corresponding interface, with no mandated fixed scheduling time base or execution delay requirement.

No custom communication bus types, data types, or data representations are defined within the impl::wheel package. All required bus access features declared across all wheel component types reference the common::pressure.i bus instance defined in the dependent common package. All bus access features use the required access mode, meaning wheel components function exclusively as bus access requesters and do not act as bus service providers. For error modeling, the NoService error type used across all error propagation and transition logic is a predefined type from the WBSImplementationErrorLib, used to represent a total loss of pressure supply service from a connected bus. The Twostate behavior model applied to both wheel variants defines a minimal two-state operational lifecycle for components, with no intermediate degraded states defined.
