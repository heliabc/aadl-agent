A public AADL package named functional::Hydraulic shall be defined, with an explicit import dependency on the functional::GenericFunctions package. The package shall contain one system type component named Hydraulic, which inherits all structural and property definitions from the functional::GenericFunctions::Generic system type. The package shall also contain one system implementation component named Hydraulic.basic, which inherits all implementation-level definitions from functional::GenericFunctions::Generic.basic and is designated as the basic implementation variant of the Hydraulic system type.

The Hydraulic system type shall define two error propagation ports as its external interface. The processor port shall be configured as an inbound error propagation port that accepts error inputs of the AnyFunctionalError type. The isFailing port shall be configured as an outbound error propagation port that transmits errors belonging to the HydraulicErrors type set. The Hydraulic system type shall integrate an EMV2 annex to define internal error behavior and propagation logic. Within the EMV2 annex, the WBSFunctionalErrorLib error type library shall be referenced, and the Twostate error behavior definition from that library shall be enabled for the component. The system shall define one error source and three cross-component error paths as part of its propagation logic. The error source f1 shall be bound to the isFailing outbound port, covering all error types in the HydraulicErrors set. Error path f2 shall map AnyFunctionalError inputs received on the processor inbound port to HydraulicLossBlue errors for transmission via the isFailing port. Error path f3 shall map AnyFunctionalError inputs received on the processor inbound port to HydraulicLossGreen errors for transmission via the isFailing port. Error path f4 shall map AnyFunctionalError inputs received on the processor inbound port to HydraulicLossComponents errors for transmission via the isFailing port. For internal component error behavior, the system shall implement two states aligned with the Twostate behavior pattern: Operational and Failed. Three internal error events shall be defined, namely GreenPumpError, BluePumpError, and ComponentError, with all three events associated with error types in the WBErrorSet. Three state transitions shall be specified: when the system is in the Operational state, activation of the GreenPumpError event shall trigger a transition to the Failed state; activation of the BluePumpError event shall trigger a transition to the Failed state; activation of the ComponentError event shall trigger a transition to the Failed state. Three outbound error propagation rules for the Failed state shall be specified: when the system enters the Failed state with no additional guard condition, the system shall propagate HydraulicLossBlue, HydraulicLossGreen, and HydraulicLossComponents errors respectively via the isFailing outbound port.

All data flows within the Hydraulic system are limited to error information transmission defined in the error model, as no functional data ports, event ports, or event data ports are specified for the component. Error data flows follow two distinct transmission paths. First, functional errors associated with external processing elements enter the Hydraulic system via the processor inbound error port, are mapped to hydraulic-domain specific error types through internal error mapping logic, and are transmitted out of the system via the isFailing outbound port. Second, internal error events corresponding to green pump faults, blue pump faults, and generic hydraulic component faults trigger a system state transition from Operational to Failed, after which the corresponding hydraulic fault types are transmitted out of the system via the isFailing outbound port. The Hydraulic.basic system implementation shall contain no internal subcomponents, port connections, or functional flow logic, serving as a minimal base implementation of the Hydraulic system type.

No explicit periodic scheduling rules, task priority assignments, execution time budgets, or end-to-end latency constraints shall be defined for the Hydraulic system or its basic implementation. Occurrence distribution properties shall be assigned to specified internal error events to support reliability analysis. The GreenPumpError and ComponentError events shall follow a Poisson occurrence distribution, with a probability value of 3.3e-5 per operational exposure interval, calculated in accordance with the guidance provided on page 49 of the AIR6110 standard. No explicit occurrence distribution property shall be assigned to the BluePumpError event in the current system definition.

No custom application data types or communication bus components shall be defined within the functional::Hydraulic package. All information transmitted across system interfaces consists of error type values referenced from external model libraries. The processor inbound error port shall carry values of the AnyFunctionalError type, representing the full set of generic functional errors propagated from upstream components. The isFailing outbound error port shall carry values of the HydraulicErrors type set, which includes the three concrete error types HydraulicLossBlue, HydraulicLossGreen, and HydraulicLossComponents. Internal error events shall carry values belonging to the WBErrorSet type. All referenced error types are sourced from imported dependent packages and external error model libraries, with no local type redefinition or override permitted. No bus instances, bus connections, or data component instances shall be included in the Hydraulic.basic implementation.
